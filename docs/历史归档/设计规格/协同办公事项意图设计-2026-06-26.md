# 协同办公事项意图设计

> 日期：2026-06-26。本文描述旧 BSCLI 原型中的事项意图预检，运行入口已退役，设计原则
> 已迁入当前 AgentBridge 受控能力模型。

## 目标

让智能体通过“批准事项”“归档事项”“参加会议”等业务意图准备写操作，而不是选择页面动作名。
系统应解析当前待办、读取页面证据并报告内部动作绑定；预检阶段不得执行任何业务写入。

## 历史设计

第一层入口是事项预检。它按事项标识或关键词唯一定位一条待办，读取既有流程证据，把业务
意图映射到内部动作，并返回一份只读执行契约。

第二层入口是确认执行。普通待办在执行前重新进行预检，只有决策为“可执行”时才委托给
受治理写入实现；会议参加、拒绝或暂定意图则定位单个会议后委托会议回复实现。

首批接收处理意图包括：

- **批准**：内部曾绑定到 `ContinueSubmit`，只有页面提供该动作且动作注册表已提升时可执行。
- **归档**：内部曾绑定到 `Archive`，当时即使页面提供该动作也只允许演练，不允许真实执行。
- **参加、拒绝、暂定**：定位单个会议邀请后进入会议回复契约。

底层动作名只用于诊断、审计和内部绑定，对外事项命令不要求智能体了解这些名称。

## 安全规则

事项预检必须满足：

- 不排队浏览器扩展任务；
- 不向协同办公系统发送写请求；
- 不调用任何写接口；
- 明确返回“不会执行”和“未发送请求”；
- 意见内容不在日志中回显，只记录必要的长度或摘要。

事项执行必须重新解析目标，要求明确确认，并遵循动作注册表给出的状态：

| 状态 | 含义 |
| --- | --- |
| 可执行 | 动作已通过提升要求，可以进入受控执行 |
| 仅演练 | 只生成计划和证据，不发送业务请求 |
| 已阻止 | 页面缺少动作、目标不唯一或契约条件不满足 |

## 对当前架构的影响

该设计验证了“对外暴露业务意图、内部封装页面原子动作”的方向。当前实现进一步按具体事项
组织能力，并使用字段卡、授权卡、能力权限、执行后核验和跨端任务时间线完成闭环。

新增事项仍应先定义业务语义和字段契约，再绑定底层接口；不能因为页面出现同名按钮就复用
其他表单的提交实现。
