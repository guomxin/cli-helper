# 旧协同办公写入探索记录

> 本文汇总旧浏览器桥时期的探索方法与已验证线索，仅用于追溯。旧扩展、localhost
> 守护进程和代理型 CLI 已退役，不得重新启用。当前系统适配资料见
> [协同办公事项能力矩阵](../系统适配/协同办公系统/事项能力矩阵.md)。

## 当时采用的探索路线

早期探索以用户已登录的真实页面为观察入口，按以下顺序收集证据：

1. 从“我的模板”“更多模板”、待办、已办、已发和跟踪事项中归类业务事项。
2. 打开列表和详情，记录事项标识、流程标识、表单类型、按钮和字段来源。
3. 观察页面发出的请求，区分列表读取、详情读取、表单初始化、保存、提交和核验接口。
4. 保存可重复的只读证据，再把候选接口整理成内部动作契约。
5. 经过模拟、单元测试和真实受控验证后，才提升为对外业务能力。

探索页面只负责发现事实，不直接等同于生产执行。Playwright 浏览器与真实用户 Chrome
曾受协同办公系统单会话限制，不能假设两套浏览器同时保持登录。

## 三层能力组织的历史演进

旧原型曾把能力分为三层：

- **通用页面动作**：页面请求、DOM 读取和表单提交等底层机制。
- **发现动作**：根据保存的页面与接口元数据生成临时可运行命令。
- **正式业务能力**：按请假、出差、补签、会议等事项提供稳定语义。

实践表明，对智能体最有价值的是第三层。底层原子动作仍可作为内部执行绑定和诊断证据，
但不应要求智能体选择 `ContinueSubmit`、`Archive` 或某个页面函数名。

## 读取侧发现

探索确认协同办公系统存在彼此独立的业务视图：

- 待办事项：当前用户尚未完成的接收处理任务；
- 已办事项：当前用户已经处理过的事项；
- 已发事项：当前用户发起的流程，可用于状态跟踪和受控撤销；
- 跟踪事项：用户主动关注的流程集合；
- 我的模板：常用发起流程入口；
- 更多模板：不在首页展示的完整模板集合；
- 文档中心：专利、软件著作权等证书扫描件的检索和下载入口。

这些列表不能混用。每种视图都应保留自己的查询条件、分页语义和返回类型。

## 接收处理侧发现

历史上完成过只读分析或受控验证的类型包括：

- 补签申请单；
- 周报发送流程；
- 加班申请审核单；
- 效能数据流程；
- 普通协同事项；
- 面试审批单；
- 劳动合同续签表；
- 知识产权申报审批单；
- 会议邀请。

同一“同意”意图在不同事项中可能需要不同表单参数和请求序列，因此当前实现采用
“事项适配器 + 受控执行生命周期”，而不是一个万能审批接口。

## 发起处理侧发现

历史上重点研究或验证过的发起类型包括：

- 请假申请；
- 出差申请；
- 补签申请；
- 新建会议；
- 用印申请；
- 业务结算、餐费报销和差旅费报销等复杂表单。

其中差旅费报销需要关联已批准的出差申请，采购合同审批字段和附件关系更复杂，因此被
明确后置。这个经验说明，能力扩展应按业务频率和可验证性排序，不能只按页面是否存在模板排序。

## 已发流程撤销契约

探索确认“已发事项”支持选择一个或多个流程后执行撤销。正式契约必须：

1. 重新读取已发列表并唯一定位目标，不能沿用旧页面位置。
2. 显示流程标题、发起时间和撤销影响，取得独立授权。
3. 执行后重新读取已发或流程详情，确认状态已经变化。
4. 若提交结果不明确，则停止并要求核对，不自动重复撤销。

该能力后来成为真实写入测试的重要收尾手段：提交测试流程、核验成功，再在用户授权范围内撤销。

## 失败经验

- 只保存接口地址而不保存字段来源，无法稳定复现复杂表单。
- 把页面按钮名直接暴露给智能体，会造成业务语义混乱。
- 仅依赖 HTTP 状态码不能判断流程是否真正提交。
- 登录卡完成后不续办原任务，会迫使用户重复发问。
- 批量处理若只跟踪第一条交互，其余卡片容易丢失或长期停留在进行中。
- 浏览器扩展频繁重载严重降低验证效率，也不适合手机和多用户部署。

## 对当前实现的影响

当前中心化实现继承了以下成果：

- 用系统适配器保存稳定业务契约；
- 用能力注册和权限范围控制对外暴露；
- 用 Credential Broker 管理每个用户、每个系统的登录会话；
- 用可信字段卡和授权卡承载敏感交互；
- 用任务时间线同步网页、Telegram 和微信；
- 用执行后核验和结果未知状态阻止重复写入。

后续发现新动作时，应按照[写入能力扩展手册](../系统适配/协同办公系统/写入能力扩展手册.md)
开展，不再追加本历史记录。
