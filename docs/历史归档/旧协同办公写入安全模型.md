# 旧协同办公写入安全模型

> 本文是旧浏览器桥时期的历史决策摘要。Chrome 扩展和本地守护进程已于
> 2026-07-13 退役，文中的旧命令、旧工具名和执行入口不得用于当前系统。
> 当前写入规则以[受控写入模型](../架构设计/受控写入模型.md)为准。

## 保留本文的原因

早期原型证明了遗留协同办公系统可以在不修改目标系统的前提下完成真实写入，也暴露出
“页面上都有提交按钮，不等于所有流程都能用同一种接口提交”的事实。本文保留当时形成的
安全原则，便于后续适配人员理解当前治理模型为何如此设计。

## 历史安全边界

旧实现把写操作划分为四个阶段：

1. **准备**：读取当前页面、流程和字段，形成待执行计划，不发送业务写请求。
2. **授权**：向用户展示业务语义、目标事项、关键字段和风险，取得一次性确认。
3. **执行**：使用受控会话发送一次业务请求，并记录幂等标识和请求证据。
4. **核验**：重新读取列表或详情，确认目标系统中的最终状态。

任何一步缺少证据，都不得把操作报告为成功。网络超时、页面跳转或接口返回结构不明确时，
结果必须进入“未知”状态并停止自动重试，避免重复提交。

## 页面探索与业务执行分离

历史实现区分两类动作：

- **发现动作**：读取页面结构、按钮、表单字段和请求线索，只产生候选契约。
- **执行动作**：只有完成字段映射、错误语义、幂等策略和真实验证后，才可提升为正式能力。

页面上发现的按钮名、JavaScript 函数名或接口地址只是一条证据，不能直接成为智能体工具。
同名的“提交”“保存”“同意”在不同表单中可能对应不同参数、不同接口甚至不同事务顺序。

## 写入计划应包含的内容

历史计划结构至少记录：

- 目标系统、用户主体、下游账号和会话标识；
- 业务事项类型、事项标识和预期动作；
- 用户可填写字段、系统自动计算字段和只读字段；
- 准备阶段取得的页面与接口证据；
- 需要展示给用户的确认摘要；
- 幂等键、计划有效期和授权有效期；
- 提交后的核验条件与失败判据。

密码、Cookie、验证码、Bearer Token 和完整页面凭据不得进入计划、日志或智能体上下文。

## 风险分级

| 等级 | 典型动作 | 历史处理原则 |
| --- | --- | --- |
| 低 | 保存草稿、修改未提交内容 | 可生成字段卡，仍需明确保存目标 |
| 中 | 审批同意、发送会议、正式提交 | 必须展示确认卡并执行后核验 |
| 高 | 撤销、归档、删除或不可逆动作 | 单独授权，不得与前一操作共用确认 |

当前平台已把这些原则落实为能力权限、可信交互、审计记录和写暂停机制，不再依赖旧 CLI
参数来保证安全。

## 能力提升条件

一个候选写动作只有同时满足以下条件，才能对智能体开放：

1. 已识别明确的业务语义，而不是只知道页面按钮名。
2. 已区分用户填写字段、系统派生字段和只读字段。
3. 已确认请求方法、必要参数、来源校验和会话依赖。
4. 已定义成功、业务拒绝、登录失效、超时和结果未知的语义。
5. 已提供准备、授权、执行、核验和审计测试。
6. 已在真实系统中完成一次受控验证；正式提交后需要能够核验，测试流程还应在允许时撤销。

未达到条件的动作只能停留在只读发现或草稿阶段。

## 已验证的历史结论

- 普通待办审批不能仅凭一个通用“同意”接口覆盖所有表单。
- 发起流程与接收处理是两类不同契约，应按具体事项组织，而不是向智能体暴露底层原子动作。
- 会议、补签、请假、出差等流程的字段和提交链路各不相同。
- 撤销已发流程必须是独立能力，重新选择目标并再次授权。
- 归档动作当时没有满足真实执行条件，因此只允许分析，不允许执行。
- 批量处理应为每个事项建立独立计划和结果，不能用一次确认掩盖多条业务写入。

## 迁移到当前架构

旧模型中仍有效的原则已经迁入中心 AgentBridge：

- 能力由服务端注册表和权限范围控制；
- 凭据由中心凭据代理保管；
- 可信卡片承载字段填写与最终授权；
- 多端只共享任务和交互状态，不共享底层凭据；
- 每次写入都有任务、交互、执行和核验记录；
- 结果未知时停止，不进行盲目重试。

当前扩展写能力时，应使用[写入能力扩展手册](../系统适配/协同办公系统/写入能力扩展手册.md)，
不要恢复本历史文档中的任何旧运行路径。
