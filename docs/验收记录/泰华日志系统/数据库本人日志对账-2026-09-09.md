# 泰华日志数据库本人日志对账

> 日期：2026-09-09，15:37—15:41（Asia/Shanghai）。
>
> 结论：一个已登录用户、一个完整周的日志 ID、日期、类型、工时和项目对账一致；发现时间精度与空值差异。不能据此认定普通用户权限、全部状态规则或团队分析已验收。

## 1. 方法与范围

用户确认无法提供后端源码，因此采用现有中央 API 与只读数据库相互对照，不推测完整后端算法。

本轮使用既有 Telegram 身份绑定，经 AgentBridge 的 `taihua_session_status` 确认应用会话 active、中央主体为 `guomao`、下游显示身份为辛国茂。未新建登录，也未使用数据库凭据登录业务 API。

固定日期窗口为 2026-08-31 至 2026-09-06，API 使用闭区间；数据库使用 `[2026-08-31, 2026-09-07)`。只核对本人日志，未扩大到其他人员或部门日志。

步骤如下：

1. 调用 `taihua_work_log_my_list`，最多 500 条，读取该周本人日志。
2. 用 API 返回的三个日志 ID 在数据库按主键定位，确认都属于唯一 user.id，再核对人员显示名。
3. 在该 user.id 和相同日期窗口内，用只读 REPEATABLE READ 事务读取全部状态的少量数值字段，并执行独立聚合。
4. 再次读取本人 API，确认选择字段前后未变；调用 `taihua_work_log_team_list`，同时限定该人员、部门及相同日期。
5. 对 ID、条数、所有者、日期、类型、工时、项目、时间及 SQL 聚合与明细进行离线断言。

API 本身返回正文等字段；脚本仅保留 ID、日期、类型、工时、人员/项目 ID 和时间，不将正文写入本机证据或输出。数据库没有选择正文、认证字段、令牌或其他人员信息。密钥只在进程内使用，未建立持久凭据文件。

## 2. 身份与结果

本人 API 日志在数据库映射到唯一应用 user.id `300002517`，用户名 `xinguomao`。团队接口解析后的 member 也返回同一 ID、用户名及部门 `300000106`（人工智能研发中心）。身份映射依据是已认证 API 返回记录的所有者以及团队成员核对，不是数据库账号的同名假设。

| 日志条数 | 3 | 3，total=3 | 3 |
| 登记工时合计 | 3.5 | 3.5 | 3.5 |

独立 SQL 聚合与逐条 Decimal 累加一致；日期、类型、工时和项目字段逐条一致。本人 API 在数据库读取前后选择字段保持一致。该窗口结果远低于接口上限，数据库同人同窗集合亦为 3 条；该样本未发现截断或漏项，不能推广为所有窗口都完整。

这些数值仅用于日志读取对账，不代表实际工作时长、出勤或绩效。样本全部无项目，尚未证明项目关联和多项目去重逻辑。

## 3. 已确认的类型字典

数据库 `dict_type` 中查到 `WORK_LOG_TYPE`（日志类型）。对应字典项为：

| item_code | item_name | status |
| --- | --- | --- |
| DAILY | 日报 | true |
| WEEKLY | 周报 | true |

一期结构化查询应明确选择日志类型，不能直接对所有 type_code 混合汇总。日报和周报工时是否存在覆盖关系仍需业务证据；默认推荐显式查询“日报登记工时”，而非宣称已经证明周报重复计入。

字典状态为 true 不足以解释所有业务表 status 的含义。

## 4. 时间差异与状态边界

三条记录均有如下差异：

- API 的 createdAt 只到秒；数据库 created_at 含小数秒。将数据库时间投影到秒后样本一致，精确值并不相同。
- API 的 updatedAt 均为空；数据库 updated_at 均非空，且在本样本中等于 created_at。
- 有一条记录的创建日期晚于日志日期。只能称为“创建日期晚于日志日期”，不能判为迟报，也不能据此确定提交截止规则。

最初的精确时间字段断言报告 6 项差异，后续将核心业务字段一致与时间表现差异分开记录，没有把时间字段改写成一致。数据库层保留原始时间精度及空值；API 投影兼容性另行处理。

三条样本 work_log.status 均为 true，没有观察到 status=false 的同范围样本。因此只证明这三条 true 记录对当前用户可见，不能发布“false 全部不可见”或“true 等于正式提交”的全局规则。

## 5. 权限结构的本用户核对

只读取当前用户相关的角色与关系配置：

- 角色为 ADMIN、EMPLOYEE，且对应角色 status=true。
- `user.dept_id` 有值；当前用户的 `dept_users` 中没有记录。团队 API 返回的部门与 user.dept_id 一致。本样本不能推导所有人员都忽略 dept_users。
- 当前用户所属部门没有查到以其为 viewer 的 `team_log_visibility_rule` 记录。
- 当前用户没有 `user_review_depts` 记录，也没有以其为所有者的关注组。

当前身份有 ADMIN 角色，即使接口成功也无法区分管理员例外、本部门默认规则和普通员工规则。未查询其他人的日志来推断权限，更未将这些空关系解释为“所有用户都能看全库”。

普通员工的部门层级、跨部门规则、可审阅部门、项目可见性和关注组共享语义，仍须通过合法可用的普通用户会话和现有界面/API 逐项验证。

## 6. 执行与检查

数据库事务保持 read_only=on、repeatable read、statement_timeout=5s，12 项固定读取均成功。每项客户端测得耗时约 0.7—6.2ms，仅代表这个小样本和当时环境，不能当作并发或大窗口性能承诺。

本机离线核对 10 项核心断言通过，精确时间差异另列。查询未做写入、账户变更或序列调用。中央服务按正常读取流程更新其自身会话活动和操作记录。

第一次 API 回读脚本在输出完成后，显式进程退出触发 Windows Node/libuv 断言；改为正常退出后重新执行只读回读，退出码为 0，数据前后仍一致。没有因此重放业务写入。

证据保存在 `output/taihua-db-validation-20260909/`：

- `api_personal_week.json`：脱正文后的原始本人 API 样本。
- `personal_db_validation.json`：本人数据库记录、聚合、字典、当前用户配置及查询耗时。
- `api_recheck.json`：本人回读和团队“仅本人”对照。
- `reconciliation_result.json`：核心断言与时间差异。
- 无凭据的读取、验证和离线核对脚本。
