## 问题与修复

生产 dispatch `4ad48cc9-ddc1-4569-84ce-f4a5e1dd5256` 在 11:53 被标记 failed / HOST_RUN_RESULT_UNAVAILABLE，但后台分析、导出随后成功，宿主同一 run 的历史记录也存在最终答复。原因是已接收请求的连接中断后只做有限几次历史查询，窗口结束就按失败终止了跟踪；这并不证明宿主执行失败。

已接收请求现在保持 accepted，按持久化 next_attempt_at 每 10 秒观察同一会话、同一 run 的历史结果。观察后释放租约，不重发 chat.send，不重复增加发送次数；中央重启后继续观察。恢复提示只写入一次，刷新页面仍可显示。收到最终答复后按原 run 的幂等消息键交付。

恢复期限从 accepted_at 起算 30 分钟，与接收前连接期限分开。期限内没有最终证据不标记失败；期限后使用 result_unknown，明确结果未确认、禁止自动重发。前端尊重显式 safeToRetry=false，即使没有收到工具进度也不提供安全重试。已接收请求遇到内部协调异常不会落入 failed_before_accept。
