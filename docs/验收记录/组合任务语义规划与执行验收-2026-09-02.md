## 二、实现内容

1. 共享规划规则不再依赖“总结、整理”等关键词；组合多个业务来源时进入持久计划。
2. `agentbridge.task-plan.proposal.v2` 支持多个结构化来源、明确时间约束和注册转换。
3. OA 已办与已发分别按处理日期和发起日期读取，经 `merge_work_items.v1` 合并。
4. 只读计划允许有限结果以 `preview_ready` 完成，同时保留 `coverage=partial` 和
   `source_incomplete=true`；计划含写入终点时仍在写入前以 `PLAN_SOURCE_INCOMPLETE` 停止。
5. `source_summary` 终态投影自包含受控事项、来源摘要和覆盖率；宿主从
   `plan.resultProjection.result` 作答，不再翻查底层 Operation。
6. `PLAN_REQUIRED` 提供一次有界修正：宿主读取目录后提交 v2 计划，不重复调用被阻断的业务能力。
7. 计划目录首先给出准备规则和只读三步示例，普通汇总不再被错误引导成日志草稿。

## 五、途中发现和修复

第一次部署后的只读计划已经能够 3/3 完成，但终态投影只有数量与覆盖率，没有事项明细。模型为了写出
标题又读取了两个来源 Operation。业务结果没有失败，但计划并不自足，也削弱了结果冻结边界。

修复后，`source_summary` 投影增加有界事项和不完整标记，成功结果增加
`report_plan_result + doNotQueryOperations` 指引。第二次真实执行只经过一次计划 prepare，随后直接形成
答案。此前只读来源 `partial` 被当成计划失败的问题也已拆分：只读警告完成，任何派生写入继续硬停。

发布时第一次 OpenClaw 热路径为 60.921 秒，略过 60 秒发布门限，固定发布器因此停止且未推送。
独立冷热复测为 66.000 秒和 27.257 秒，确认只是首次冷启动；随后不重复重启已热起的 Gateway，固定
发布器完成健康检查、部署和 GitHub 回读。没有放宽门限或修改网络配置。

## 七、剩余边界

1. OA 已办目前只扫描首批 50 条，指定日期范围仍可能是 `partial`；下一步应补有界多页遍历和可证明
   日期停止条件，不能把当前两条结果宣传为全历史完整集合。
2. 含泰华日志写入终点的 v2 计划本轮没有真实提交。自动化已证明部分来源会在写前停止，真实正向写入
   仍需明确日志内容、工时和一次性授权。
3. Telegram、微信跨端确认和第二用户组合计划本轮没有重复验收；应在查询增强后做扩展回归，不操作
   第二用户真实待办。
4. 当前仅验证两种自然说法。更多同义表达继续按工作台验收方案抽样，不为每个词增加规则分支。
