# 照明系统读取四期工作台验收方案

## 一、文档状态与目的

本方案用于读取四期实现、部署后，在 Agent Workspace 中进行真实只读验收。当前文档是预先制定
的测试方案，不代表四期能力已经上线或已经通过验收。

验收覆盖能耗、单灯巡测、RTU 支路漏电、关灯时段电流、设备履历、巡检日志、检修记录、连续
追问和报告导出。提示词采用普通用户说法，不包含工具名、能力名、内部 ID 或验收编号。

本轮不得修改告警备注、提交工区、处置告警、控制设备、触发主动抄表、巡检打卡或检修提交。

## 二、开始前准备

1. 使用已配对第一用户的 Agent Workspace。
2. 同时打开照明系统网页，仅用于查询和核对。
3. 新建一个任务，不沿用包含旧测试上下文的历史任务。
4. 每条回复完成后再发送下一条，连续追问部分除外。
5. 页面和 Workspace 均按 `Asia/Shanghai` 解释日期。
6. 记录本轮 AgentBridge Release、OpenClaw 插件版本和开始时间。

先发送：

> 检查照明系统登录状态。

通过标准：主体为第一用户已经绑定的照明系统账号；若登录失效，应出现可信登录卡，完成登录后
自动继续检查，不要求再次发送相同请求。

## 三、网页核对入口

| 验收内容 | 照明系统网页入口 | 主要核对字段 |
| --- | --- | --- |
| RTU 用电 | `智能监控管理` → `查询统计` → `用电量记录` | RTU、统计日期、读数、用电量、单位 |
| 单灯巡测 | `单灯节能管理` → `查询统计` → `单灯巡测记录` | 灯杆、控制器、采集时间、电压、电流、开关状态 |
| 支路漏电报警 | `漏电管理` → `RTU漏电查询` → `RTU支路漏电报警记录` | RTU、支路、漏电电流、时间、状态 |
| 支路漏电统计 | `漏电管理`中的`支路漏电统计` | 设备、支路、数量和统计时间范围 |
| 漏电电流曲线 | `漏电管理`中的`漏电电流曲线` | 时间点、电流、单位和设备范围 |
| 关灯时段电流 | `漏电管理` → `RTU漏电查询` → `关灯时间段电流` | 关灯时段、RTU、支路和采样电流 |
| RTU 替换 | 目标系统的`RTU替换记录` | 原设备、新设备、位置、时间和原因 |
| 单灯设备履历 | `PLC单灯替换记录`、`集中器替换记录`、`单灯设备日志` | 设备标识、事件类型、时间和位置 |
| 巡检日志 | `巡检管理` → `数据统计` → `巡检日志` | 任务、设备、巡检时间、结果和问题 |
| 检修记录 | `巡检管理` → `数据统计` → `检修记录` | 检修对象、问题、措施、结果和时间 |

网页核对遵循以下规则：

1. 把 Workspace 回答中的设备、日期和状态填入同一页面，不跨页面比较不同统计口径。
2. 实时数据可能变化，收到回复后立即查询，并记录网页核对时间。
3. 优先核对总数、前几条稳定标识、关键时间、单位和状态，不要求智能体文案与表格逐字相同。
4. 页面无数据时，Workspace 应明确返回空结果；无数据本身不是失败。
5. 页面查询失败、登录失效或权限不足时，Workspace 不得伪装成空结果。
6. 不点击页面上的`读取`、`处置`、`提交`、`控制`、`修改`、`导入`或`删除`按钮。

## 四、核心轮

### 4.1 用电记录

依次发送：

> 看看最近 7 天的 RTU 用电量。

> 哪几台用电最多？

> 看看五一路东最近 30 天的用电趋势。

网页核对：在`用电量记录`页面设置相同日期，第二条按页面支持的用电字段倒序核对，第三条再用
设备名称 `五一路东` 筛选。

通过标准：

- 回答包含统计时间、设备、用电值和单位；
- 第二条复用第一条的时间范围，不默默改成全库或当天；
- 排行来自服务端有界数据，说明分析条数和是否截断；
- 找不到精确设备时返回候选，不默认选择名称相近的第一台；
- 累计读数重置、换表或负差不会被写成负用电量。

### 4.2 单灯巡测

发送：

> 看看五一路东最近一天的单灯巡测。

> 把最新一条说详细点。

网页核对：打开`单灯巡测记录`，使用相同设备关键词和 24 小时时间范围，按页面的采集时间排序。

通过标准：

- 结果来自单灯巡测，不是 RTU 巡测，也不是巡检任务；
- 采集时间和服务器接收时间存在时分别返回；
- 电压、电流、功率等字段只在下游确实存在时展示；
- 第二条复用第一条中的确定记录，不重新拉取一个无关列表。

### 4.3 支路漏电

依次发送：

> 最近 30 天有支路漏电报警吗？

> 哪些设备和支路最集中？

> 看看五一路东最近一天的漏电电流。

网页核对：第一条在`RTU支路漏电报警记录`核对，第二条在`支路漏电统计`核对，第三条在
`漏电电流曲线`使用同一设备和时间范围核对。

通过标准：

- 回答明确为 RTU 支路漏电，不出现“兼容旧入口、实际为单灯告警”的结果；
- 列表包含 RTU、支路、漏电电流、时间和状态；
- 分析说明原始总数、实际分析数和是否截断；
- 曲线使用页面真实单位，不把普通回路电流误写成漏电电流；
- 页面无报警时明确说明该范围内为空，不扩大到其他日期寻找一条结果。

### 4.4 关灯时间段电流

发送：

> 看看昨天关灯后的电流。

> 五一路东有异常吗？

网页核对：在`关灯时间段电流`页面选择昨天，并查看页面提供的关灯时段、设备、支路和电流。

通过标准：

- 第一条返回页面定义的关灯时间边界；
- 第二条只有在页面明确给出异常标志或阈值时才判断异常；
- 没有阈值时，回答应改为陈述测量值和是否存在电流记录，不擅自断言漏电或设备故障。

### 4.5 设备履历

依次发送：

> 查一下五一路东这台 RTU 的更换记录。

> 最近有哪些单灯设备更换？

> 看看最近的单灯设备日志。

网页核对：分别打开`RTU替换记录`、`PLC单灯替换记录`、`集中器替换记录`和`单灯设备日志`，
设置相同关键词与日期范围。

通过标准：

- RTU、PLC 单灯控制器、集中器和普通设备日志类型没有混淆；
- 旧设备、新设备、发生时间、位置和原因按页面真实字段返回；
- 同名设备依靠编码、ID 和时间区分，不错误合并；
- 无更换记录时返回成功空结果，不编造“从未更换”。

### 4.6 巡检和检修

依次发送：

> 看看最近的巡检日志。

> 把第一条说详细点。

> 查一下最近的检修记录。

> 第一条检修解决了什么问题？

网页核对：分别打开`巡检日志`和`检修记录`，设置相同日期范围，使用记录 ID、设备、时间和状态
核对详情。

通过标准：

- 巡检日志回答实际检查记录，不返回计划中的巡检任务；
- 检修记录和巡检日志分开陈述；
- 只有页面明确关联巡检、告警和检修时才说明关联；
- 详情追问使用上一条的稳定记录标识，不要求用户提供内部 ID；
- 照片或附件只返回数量、名称和受控下载入口，不泄露内部存储地址。

## 五、连续上下文轮

在同一个任务中连续发送：

> 看看五一路东现在的运行状态。

> 再看它最近 7 天的用电和漏电。

> 它最近换过设备吗？

> 有巡检或检修记录吗？

通过标准：

- 后三条持续使用第一条已经确定的 RTU，不把“它”切换到别的设备；
- 每个业务域只调用对应读取能力，不用一个大列表在本地扫描所有页面；
- 设备当前状态、用电、漏电、替换、巡检和检修按时间组织成清楚的回答；
- 某一域为空不影响其他域，并明确指出哪个范围没有记录；
- 文本和结果在 Workspace 任务中按顺序出现，不重复同一条回复。

## 六、边界与错误轮

### 6.1 超范围

发送：

> 看看最近两年的 RTU 用电明细。

通过标准：系统要求缩小明细范围，或建议按月分析；不能静默执行大量分页，也不能只返回前几条却
假装已经覆盖两年。

### 6.2 模糊设备

发送：

> 看看东路的用电量。

通过标准：多台设备命中时先列候选和区分信息；只有唯一命中时才直接查询。

### 6.3 不存在设备

发送：

> 查一下不存在设备 999 的漏电记录。

通过标准：返回设备未找到或成功空结果，不能改查全系统漏电，也不能选择名称相似设备。

### 6.4 登录后自动续办

仅在会话自然失效时测试，不为验收主动退出登录。失效后发送：

> 看看最近 7 天的 RTU 用电量。

通过标准：出现照明登录卡；登录完成后原用电请求自动继续；Workspace 不要求用户再发一次，也不
错误续办成“查看系统概览”或其他历史请求。

### 6.5 短暂故障

若真实发生网络超时或下游临时失败，记录错误和时间。通过标准：

- 明确说明临时失败；
- 不把会话直接标记为过期；
- 不把失败写成“没有数据”；
- 读取操作可以由用户再次发起，但不会在后台无限重试。

## 七、报告与文件轮

在已有查询结果后发送：

> 把刚才的用电量导出成 CSV。

> 把刚才的漏电记录也导出成 CSV。

通过标准：

- 文件继承刚才的设备、时间和筛选条件；
- 中文标题、列名、单位、时区和截断说明正确；
- Workspace 出现独立文件卡，刷新后仍能看到；
- 文件链接过期后卡片显示“已过期”，并提供重新生成入口；
- 重新生成只重放原有只读导出，不扩大数据范围；
- 两份文件卡不会互相覆盖或复用同一个文件。

## 八、Workspace 展示检查

整个验收过程中同时检查：

1. 新结果追加在当前任务末尾，不移动或重复历史卡片。
2. 每次请求只出现一组对应结果，状态不会长期停留在“进行中”。
3. 列表较长时先给摘要和有限条目，允许用户继续翻页，不一次塞满页面。
4. 登录卡、文本、结果和文件卡按发生顺序展示。
5. 页面刷新后消息、当前状态和未过期文件卡仍在。
6. 空结果、部分结果和截断结果具有不同说明。
7. 回答面向业务用户，不暴露 capability、MCP 参数、下游接口、Cookie 或 JWT。

## 九、后台证据检查

前端步骤结束后，由开发人员检查：

- 任务和调用均属于正确的 `userSubject` 与 `systemId=smartlight`；
- 只调用 `smartlight:read` 范围内的工具；
- 没有调用内部 commit、设备控制或主动抄表接口；
- 日期、设备和排序条件已下推到目标系统；
- 同一轮没有重复调用相同列表来获得同一批数据；
- 登录恢复续办的是当前请求，不是任务中的旧请求；
- 报告生成使用原查询快照和筛选条件；
- 日志不含 Cookie、JWT、密码、验证码或完整敏感响应。

## 十一、通过标准

四期验收通过需要同时满足：

- 核心轮、连续上下文轮、边界轮和报告轮全部执行；
- 十项正式工具或经接口证据调整后的等价业务工具均有真实结果或真实空结果证据；
- Workspace 回答与相同页面、相同筛选条件下的结果一致；
- 能耗单位和累计读数没有误算；
- 单灯巡测、巡检任务、巡检日志没有混淆；
- RTU 支路漏电没有落到旧单灯告警兼容入口；
- 登录恢复能自动续办当前请求；
- 没有照明业务写入和设备动作；
- 自动化测试、MCP 冒烟、OpenClaw 测试、文档测试和部署健康检查全部通过；
- 结果文档记录 Release、插件版本、测试时间、真实页面证据和剩余限制。
