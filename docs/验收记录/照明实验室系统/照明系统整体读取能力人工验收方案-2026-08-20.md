# 照明系统整体读取能力人工验收方案

## 一、验收目的

本方案供用户在 Agent Workspace 中人工核实照明实验室测试系统的全部正式读取能力。范围
包括一期、二期和三期，不只验证新增的运行态能力。

本轮只读，不修改告警备注，不提交或撤回工区，不处置告警，也不执行设备控制。测试时使用
第一用户已配对的 Workspace；如果会话失效，可以完成照明系统登录卡，登录后应自动继续原请求。

## 二、开始前检查

1. 打开已配对第一用户的 Agent Workspace。
2. 新建一个任务，先发送：

   > 检查照明系统登录状态。

3. 若显示已登录，继续后续步骤。若出现登录卡，完成登录并观察原请求是否自动续办；不应要求
   再发一次相同请求。
4. 每条请求等当前回复结束后再发下一条，避免把串行任务误当成并发测试。

通过标准：登录主体正确；没有出现 OA、泰华或语雀的数据；页面刷新后本任务和已有回复仍在。

### 2.1 网页核对的通用方法

人工核对时同时打开 Agent Workspace 和照明系统网页。Workspace 用于发送下文提示词，照明
网页只做查询、查看和必要的只读导出，不点击处置、控制、提交、修改、批量设置等写入按钮。

| Workspace 验收内容 | 照明网页入口 | 页面主要核对信息 |
| --- | --- | --- |
| 静态系统概览 | 顶部 `设施资源管理` | 设施设备数量、类型和工区统计 |
| 实时运行概览 | 顶部 `智能监控管理` | RTU 运行指标、实时状态和报警概况 |
| RTU、控制箱、灯杆资产 | `设施资源管理` 下相应管理页面 | 编号、名称、型号、道路、控制箱、安装信息 |
| RTU 当前状态 | `智能监控管理` → `常用列表` | 在线、离线、停电、未启用、巡测时间和三相数据 |
| 单灯当前状态 | `单灯节能管理` → `单灯监控` → `运行状态` | 控制器在线状态、灯具开关和电气数据 |
| RTU 告警 | `智能监控管理` → `查询统计` → `RTU报警记录` | 首次/末次发生时间、状态、备注和告警内容 |
| 单灯告警 | `单灯节能管理` → `查询统计` → `单灯报警记录` | 灯杆、道路、告警类型、状态和首次报警时间 |
| RTU 支路漏电 | `漏电管理` → `RTU漏电查询` → `RTU支路漏电报警记录` | 漏电电流、支路、告警时间和状态 |
| RTU 遥测历史 | `智能监控管理` → `查询统计` → `RTU巡测记录` | 三相电压/电流、回路、状态、告警、温湿度 |
| 巡检任务 | `巡检管理` → `数据统计` → `巡检任务统计` | 计划、日期、设备数量、进度、巡检组和打卡记录 |

核对时遵循以下口径：

1. 先在 Workspace 得到设备名称、编号、时间范围或告警类型，再把相同条件填入网页搜索框。
2. 网页数据会变化，尽量在 Workspace 回复后立即查询；记录页面查询时间，不拿不同时间的实时
   快照做逐项相等比较。
3. 对 `最近 7 天`、`最近 30 天` 等请求，在网页中手工设置相同开始、结束日期。告警页的“当日”
   和“昨日”统计卡可能按中午 12 点切日，不可直接替代自然日范围查询。
4. 优先核对总数、前几条的稳定标识、关键时间和状态；智能体会对页面字段做中文归纳，不要求
   文案逐字一致。
5. 页面显示 `暂无数据` 时，Workspace 应返回明确空结果。不得用另一个设备、另一个页面或更大
   时间范围的数据补齐答案。
6. 静态资产页、运行状态页和统计首页各有自己的业务范围，数字不一致不直接判失败；只比较同一
   入口、同一筛选条件下的结果。

## 三、概览与口径

依次发送：

> 看一下照明系统概览。

> 照明系统现在整体运行怎么样？

网页核对方式：

1. 点击顶部 `设施资源管理`，在首页记录控制箱、灯杆、灯源、RTU、单灯控制器等“设施设备数量
   统计”，必要时下看“设施设备按工区统计”。它对应第一条静态概览。
2. 点击顶部 `智能监控管理`，在首页查看“RTU运行指标”“RTU实时状态”“今日运行情况”和
   “24H RTU报警统计”。它对应第二条实时运行概览。
3. 分别记录两个页面的查询时刻和统计标题，不把设施资源首页的资产数拿去强行匹配运行页的状态数。

核实：

- 第一条回答的是登记或地图口径的控制柜、RTU、灯杆等静态概览；
- 第二条回答的是当前 RTU、单灯控制器和灯具运行快照，包含在线、离线、停电或禁用等状态；
- 运行结果说明观察时间和统计范围；
- 不把静态资产总数和运行页面总数强行解释成同一个数字；
- 不通过“总数减在线数”编造下游没有返回的状态。

## 四、资产与灯杆

依次发送：

> 查找照明系统里的 RTU，先列 5 条。

> 查看上面第 1 台 RTU 的详情。

> 查找照明系统里的控制柜，先列 5 条。

> 查找照明系统里的灯杆，先列 5 条。

> 再看上面第 1 个灯杆的详情。

网页核对方式：

1. RTU：顶部 `设施资源管理` → `监控设备管理` → `RTU管理`，在“RTU编号”中输入 Workspace
   返回的编号并搜索。对照 RTU 名称、型号、类型、所属控制箱、分组、安装日期和出厂日期。
2. 控制箱：`设施资源管理` → `照明设施管理` → `控制箱管理`，可按名称、安装日期、设备类型、
   控制箱类型或工区搜索。对照编号、名称、设备类型、容量、道路和路侧。
3. 灯杆：`设施资源管理` → `照明设施管理` → `灯杆管理`，把 Workspace 返回的灯杆编号填入
   “灯杆编号”并搜索。对照灯杆类型、高度、灯源数量、道路、路侧、控制箱和安装日期。
4. 核对详情时，在目标行最右侧“操作”列打开查看入口；只查看，不使用编辑、删除、批量设置等按钮。

核实：

- RTU、控制柜和灯杆没有混为一种资产；
- 列表包含稳定标识、名称或编号以及所属范围；
- RTU 详情能够返回设备基本信息，并在下游有数据时返回继电器、回路等结构；
- “上面第 1 个”能沿用当前任务上下文，不要求用户填写内部任务号或工具参数；
- 空字段如实留空，不从相邻设备推断。

## 五、当前运行状态

依次发送：

> 列出前 10 台离线 RTU。

> 再看看停电的 RTU。

> 列出前 10 个离线的单灯控制器。

> 看看当前开灯的单灯，先列 10 条。

网页核对方式：

1. RTU：顶部 `智能监控管理` → `常用列表`。页面上方有总数、亮灯、灭灯、外接电电源、未启用、
   离线和电源停电统计；点击相应状态卡或使用 RTU 编号/名称、类型、型号、分组筛选，再与
   Workspace 返回的前 10 条对照。
2. RTU 表格重点核对编号、名称、状态、巡测时间、支路号、总电流、三相电流和三相电压。
3. 单灯：顶部 `单灯节能管理` → `单灯监控` → `运行状态`。使用灯杆编号、控制箱、道路等条件，
   并结合在线/离线、亮灯/灭灯统计核对结果。
4. 单灯表格重点核对灯杆名称、在线状态、道路、路侧、巡测时间以及每路灯源的开关、电压、电流、
   功率因数、有功功率和调光值。页面为 `--` 时，Workspace 也不应编造数值。

核实：

- RTU 列表按运行页面口径返回，能区分在线、离线、停电和禁用；
- RTU 项目包含最后在线时间、控制柜、分组、工作模式和告警标记等实际存在的字段；
- 单灯结果包含灯杆、控制器、道路、控制柜、RTU、在线状态和开关状态；
- 电压、电流、功率、调光值等字段只在下游真实返回时展示；
- 无结果时明确说没有命中，而不是切换到静态资产列表凑数。

## 六、RTU 告警

依次发送：

> 列出最近 5 条 RTU 告警，按发生时间排。

> 告诉我上面第 1 条告警的当前备注。

> 分析最近 30 天的 RTU 告警。

网页核对方式：

1. 打开 `智能监控管理` → `查询统计` → `RTU报警记录`。
2. 在“报警时间”填写与 Workspace 相同的开始、结束日期；需要时再设置 RTU、报警类型、报警状态、
   RTU 分组和是否去重，然后点击搜索。
3. 用页面“共 N 条记录”和 Workspace 的下游总数对照；抽查前几条 RTU 编号、名称、报警类型、
   报警内容、首次发生时间、末次发生时间、解除时间和状态。
4. “当前备注”直接核对表格“备注”列；若需要打开行详情，仅点击查看入口，不点击提交工区处置。
5. 分析结果中的趋势和排行是 AgentBridge 对当前筛选结果的有界汇总，可使用页面导出后按日期、
   类型或 RTU 透视核对，不要求网页本身存在完全相同的分析卡片。

核实：

- “最近”按首次发生时间全局排序；只有用户明确说最近活动或变化时才按最近活动时间；
- 多条告警发生时间相同时，结果顺序稳定且不会漏掉并列项；
- 状态使用“当前告警、非当前告警、已解除、已处置”等业务文字，不裸露难懂状态码；
- 告警分析说明实际分析条数、下游总数和是否截断，并返回趋势或集中设备；
- 读取备注不会弹出写入授权卡，也不会修改备注。

## 七、单灯告警与漏电语义

依次发送：

> 列出最近 7 天的单灯告警，先看 10 条。

> 分析最近 30 天的单灯告警。

> 异常亮灯有几条？

> 最近 7 天有漏电报警吗？

网页核对方式：

1. 单灯告警打开 `单灯节能管理` → `查询统计` → `单灯报警记录`，设置相同报警日期，并按灯杆、
   道路、报警类型或状态筛选。核对“共 N 条记录”和表格中的灯杆、道路、路侧、控制箱、灯源用途、
   报警类型、状态、首次报警时间。
2. “异常亮灯有几条”应在该页面把报警类型设为“异常亮灯”后搜索，不能到漏电页面查。
3. 真实 RTU 支路漏电打开 `漏电管理` → `RTU漏电查询` → `RTU支路漏电报警记录`，设置相同时间
   范围并核对 RTU、支路工作模式、报警类型、报警内容、首次/末次时间和状态。
4. 也可在 `智能监控管理` → `查询统计` → `RTU报警记录` 中把报警类型筛选为漏电类进行交叉核对。
   如果两个真实漏电入口均为空，Workspace 不应把单灯“异常亮灯”等记录当作漏电返回。

核实：

- 前三条明确称为“单灯告警”，普通的“异常亮灯”等记录不会被整体称为漏电；
- 单灯告警能按时间、类型、状态、道路、工区或控制柜筛选；
- 分析结果包含日期趋势、告警类型、灯杆、道路和状态排行，并说明是否截断；
- 最后一条优先查询 RTU 告警中的漏电类型，或说明需要指定 RTU 查看巡测漏电电流；
- 回答应明确数据来源，不使用已经弃用的旧“漏电分析”口径冒充真实漏电。

## 八、RTU 巡测记录

先从前面的 RTU 结果中选一台名称明确的设备，然后发送：

> 查看这台 RTU 最近 24 小时的巡测记录。

> 只看其中的异常记录。

> 查看这台 RTU 最近 10 天的巡测记录。

核实：

- 查询唯一锁定一台 RTU；名称命中多台时先给简短候选，不混合多台数据；
- 记录包含下游真实返回的三相电压、电流、温湿度、开关量、告警内容和漏电电流等字段；
- 默认范围是最近 24 小时，“只看异常”只筛选遥测记录；
- 10 天请求超过单次 7 天上限，应要求缩小范围，不执行无界扫描；
- 回答明确“巡测记录”是设备遥测历史，不是巡检任务。

若所选 RTU 在最近 24 小时没有数据，可改选另一台设备或换成系统页面中可见的明确时间段；
空结果本身不算失败，但不能返回另一台 RTU 的记录。

网页核对方式：

1. 打开 `智能监控管理` → `查询统计` → `RTU巡测记录`。
2. 在“RTU编号/名称”输入 Workspace 锁定的设备；在“巡测时间”填写同一时间范围。第二条测试
   再勾选“仅显示异常”，然后搜索。
3. 对照页面总记录数和各行巡测时间、RTU 名称、Ua/Ub/Uc、IA/IB/IC、开灯/关灯支路、RTU 时间、
   Ia/Ian、Ib/Ibn、Ic/Icn、A/B/C 相回路号、状态、报警内容、温度和湿度。
4. 漏电电流不一定在默认显示列中；可使用“显示列”打开下游实际提供的漏电字段。页面没有该字段
   或值为无效占位时，Workspace 必须明确空值或无有效读数。
5. 页面允许人工填写更长时间段不代表 AgentBridge 可以无界查询；“最近 10 天”被要求缩小范围
   属于预期保护，不用在网页执行 10 天扫描。

## 九、巡检任务

依次发送：

> 看看照明系统最近的巡检任务。

> 只看执行中的巡检任务。

> 查看上面第 1 个任务的每日进度和打卡记录。

网页核对方式：

1. 打开顶部 `巡检管理` → `数据统计` → `巡检任务统计`。
2. 选择与 Workspace 结果相同的巡检类型、设备类型、计划和日期后搜索。
3. 对照开始/结束时间、巡检设备总数、已巡检设备数、整体进度、工单数、巡检组数、巡检人数和
   小组任务进度。
4. 在对应任务的详情入口查看每日进度和打卡记录。注意页面上的巡检组、人数、设备数和总量完成
   占比是不同字段，不自行换算后要求 Workspace 得到同一数字。

核实：

- 待执行和执行中状态解释正确；
- 列表返回巡检组、任务日期、下游进度和设备数量等真实字段；
- 详情返回每日进度和实际打卡记录；
- 巡检组不被冒充为个人负责人；
- 不把不同口径的进度和设备数量自行组合成完成率；
- 本组请求不会误调用 RTU 巡测记录。

## 十、报告与文件交付

依次发送：

> 导出最近 30 天的 RTU 告警分析。

> 导出最近 30 天的单灯告警分析。

> 导出照明系统资产清单。

> 导出最近巡检任务的进度。

网页核对方式：

1. 先到对应来源页设置与 Workspace 相同条件：RTU 告警用 `RTU报警记录`，单灯告警用
   `单灯报警记录`，资产用 `RTU管理`、`控制箱管理` 或 `灯杆管理`，巡检用 `巡检任务统计`。
2. 记录页面总数和前 3 条稳定标识，再下载 Workspace 文件，核对文件标题、元数据、列名、行数和
   前 3 条记录。
3. 页面自身的“导出”是可选的第二份只读证据，可以用来核对原始字段；它与 AgentBridge 的标准化
   CSV 列名不必完全一致，但业务记录和筛选范围应一致。
4. 不要在不同时间重新搜索后只按行号比较；实时状态和新告警可能使行号变化，应按设备编号、告警
   时间或任务标识匹配。

核实：

- 每个请求只产生一张对应文件卡，没有重复卡片；
- 文件名和标题分别体现 RTU 告警、单灯告警、资产或巡检，不再生成“照明漏电分析”标题；
- 下载的 CSV 可打开，列名和行数与当前查询元数据相符；
- 文件卡在页面刷新后仍保留；短期下载链接过期时，卡片显示已过期并允许重新生成；
- 文件不会错投到其他用户或其他任务。

## 十一、连续追问与页面恢复

在同一任务中发送：

> 把刚才离线 RTU 里的第 1 台再查详细一点。

然后刷新 Workspace 页面，再发送：

> 继续分析刚才的单灯告警，重点看最常见的类型。

网页核对方式：保持相应来源页的筛选条件不变，用设备编号、告警时间或任务名称核对 Workspace
连续追问引用的仍是同一批记录。刷新的是 Workspace 页面，不需要刷新照明系统页面；刷新后若
Workspace 改用了其他设备或时间范围，即判为上下文接续失败。

核实：

- 连续追问沿用当前任务中的业务对象和时间范围；
- 页面刷新后文本、任务状态、文件卡和上下文仍在；
- 不重复调用同一个列表制造两份结果；
- 不要求用户提供内部 `task_id`、`interaction_id` 或工具名；
- 任务结束后显示完成，不长期停留在进行中或等待用户。
