# 照明系统整体读取能力人工验收方案

## 一、这份方案解决什么问题

本方案供不熟悉照明实验室测试系统的验收人员使用。按照章节依次在 Agent Workspace 中发送
简短请求，再到照明系统网页的指定位置核对即可。

验收范围是当前已正式开放的一期、二期和三期读取能力：

1. 登录状态与登录后自动续办；
2. 静态资产概览和实时运行概览；
3. 控制柜、RTU、灯杆的列表与详情；
4. RTU 和单灯的当前运行状态；
5. RTU 告警列表、备注和分析；
6. 单灯告警列表和分析；
7. 漏电语义辨别；
8. RTU 巡测记录；
9. 巡检任务、每日进度和打卡记录；
10. CSV 报告与文件交付；
11. 连续追问、页面刷新和历史消息恢复。

本轮全程只读。不要点击设备控制、告警处置、提交工区、撤回、备注保存、编辑、删除或批量设置。

## 二、怎样使用本方案

每个验收组都包含五类信息：

| 内容 | 用途 |
| --- | --- |
| 发送请求 | 可直接在 Workspace 中发送的自然语言，不需要工具名和内部编号 |
| 预计回答 | 智能体通常会展示的业务内容；实际数量随系统变化 |
| 数字和字段来源 | 说明数字究竟来自照明系统哪个接口，还是 AgentBridge 的有界汇总 |
| 网页核对步骤 | 告诉不熟悉系统的用户从哪个菜单进入、核对哪些列 |
| 通过标准 | 说明怎样算通过，哪些差异不能误判为失败 |

### 2.1 通用核对原则

1. 同时打开 Agent Workspace 和照明系统网页。Workspace 负责提问，照明网页只负责只读核对。
2. 收到 Workspace 回复后立即到网页查询，并记下两边的查询时间。实时状态和告警会变化，不能拿
   相隔很久的快照逐行比较。
3. “最近 7 天”按上海时区的自然日计算，包含开始日和结束日；在网页中手工填写相同日期。
4. 优先核对总数、设备编号、告警 ID、任务 ID、时间和状态。智能体会把字段整理成中文，文案不必
   与网页逐字相同。
5. `总数` 是照明系统分页结果中的 `totalCount/total`；`本次返回`只是当前页条数，两者不是一回事。
6. 资产页、地图页和实时状态页的数据范围不同。只有同一页面、同一筛选条件下的数字才应相等。
7. 页面显示 `--`、空白或暂无数据时，Workspace 也应如实显示为空或说明没有结果，不能从其他设备
   推断补齐。
8. 分析类回答最多分析 500 条。若回答出现“已截断”，排行和趋势只是有界样本，不能当作全量统计。

### 2.2 接口名称怎么看

本方案列出接口只是为了说明数据血缘，人工验收时不需要调用接口。所有正式读取都由 AgentBridge
通过当前用户的照明系统会话执行。

## 三、开始前：登录与自动续办

### 3.1 发送请求

> 检查照明系统登录状态。

### 3.2 预计回答

- 已登录时：说明登录有效、当前主体和检查时间；不会弹登录卡。
- 未登录时：出现照明系统安全登录卡；完成登录后，原来的“检查登录状态”应自动继续并返回结果，
  不需要再问一遍。

### 3.3 网页核对步骤

1. 打开照明系统首页。
2. 看页面右上角或用户菜单中的当前用户名。
3. 与 Workspace 返回的已验证主体核对。

### 3.4 通过标准

- 登录主体正确，没有混入 OA、泰华或部门信息库身份；
- 登录卡成功后自动续办原请求；
- 登录失败时返回明确原因，不静默结束；
- 刷新 Workspace 后仍保持网页账号和任务历史。

## 四、静态资产概览

### 4.1 发送请求

> 看一下照明系统概览。

### 4.2 预计回答

回答应至少包含：

- 控制柜总数；
- 灯杆的可检索总数；
- 地图或单灯运行明细口径的灯杆总数；
- 控制柜状态分组；
- 两种灯杆口径不一致时的解释。

2026 年 8 月 20 日的一次真实结果如下，仅用于理解格式，不能作为以后固定答案：

| 项目 | 当次结果 | 正确解释 |
| --- | ---: | --- |
| 控制柜 | 36 | 地图综合控制柜接口当次返回了 36 个对象 |
| 控制柜状态 `unknown` | 36 | 这批地图对象没有可用状态字段，不表示 36 台都离线 |
| 可检索灯杆 | 131 | 灯杆资产检索列表的总记录数 |
| 地图明细灯杆 | 116 | 单灯运行或地图明细列表的总记录数，范围与资产列表不同 |

### 4.3 每个数字从哪里来

| Workspace 内容 | AgentBridge 字段 | 照明系统来源 | 取数方式 |
| --- | --- | --- | --- |
| 控制柜总数 | `cabinetTotal` | `/map/getIntegratedRControlCabinetDataByCondition` | 对返回的控制柜对象逐个计数 |
| 控制柜状态分组 | `cabinetStates` | 同上 | 读取 `onlineState/state/rtuState/alarmState`；都没有时记为 `unknown` |
| 可检索灯杆 | `lampPostTotal`、`lampPostCounts.searchable` | `/lLamppost/getDataByConditionForFacilityEx` | 使用分页结果的总记录数 |
| 地图明细灯杆 | `lampPostCounts.mapDetail` | `/lLamppost/getLampDetialList` | 使用单灯运行明细分页结果的总记录数 |
| 样例控制柜 | `sampleCabinets` | 地图综合控制柜接口 | 只展示前 10 条，不代表总数只有 10 |

### 4.4 网页核对步骤

1. 点击顶部 `设施资源管理`。
2. 在设施统计区域记录控制柜和灯杆数量；若首页没有直接显示，可分别进入控制柜管理和灯杆管理，
   查看表格底部“共 N 条”。
3. 进入 `设施资源管理` → `照明设施管理` → `灯杆管理`，清空筛选条件后记录总数，对照“可检索灯杆”。
4. 再进入 `单灯节能管理` → `单灯监控` → `运行状态`，清空筛选条件后记录总数，对照“地图明细灯杆”。
5. 两个灯杆数字不同时不要判失败；先确认比较的是上述两个不同入口。

### 4.5 通过标准

- 数量能在对应页面找到来源；
- 回答明确区分两种灯杆口径；
- `unknown` 被解释为“接口没有状态字段”，而不是“设备离线”；
- 没有拿 `131 - 116` 推断缺失、故障或离线灯杆。

## 五、实时运行概览

### 5.1 发送请求

> 照明系统现在整体运行怎么样？

### 5.2 预计回答

回答应包含 RTU、单灯控制器和灯具三组当前快照。例如 2026 年 8 月 20 日的一次真实结果是：

| 组别 | 当次结果 |
| --- | --- |
| RTU | 总数 29、在线 0、离线 27、停电 1、未启用 1 |
| 单灯控制器 | 总数 118、在线 1、离线 117 |
| 灯具 | 总数 178、开灯 1、关灯 0、告警灯杆 0 |

这些数字会变化。尤其不能因为当次 `开灯 + 关灯` 不等于 `灯具总数` 就自行补算，因为下游的灯具
登记总量、实时上报开关量和控制器在线范围不是同一统计集合。

### 5.3 每个数字从哪里来

| Workspace 内容 | 下游字段 | 接口 | 网页大致位置 |
| --- | --- | --- | --- |
| RTU 总数 | `rAllCount` | `/rRtu/getRtuStateCountDataByConditionNew` | `智能监控管理` → `常用列表` 上方统计卡 |
| RTU 在线 | `rOnlineCount` | 同上 | 在线统计卡 |
| RTU 离线 | `rNoOnlineWithNoHandleCount` | 同上 | 离线统计卡 |
| RTU 停电 | `rPowerOutageCount` | 同上 | 电源停电统计卡 |
| RTU 未启用 | `rDisableCount` | 同上 | 未启用统计卡 |
| 在线有电 | `rOnlineWithEleCount` | 同上 | RTU 运行指标中的细分状态 |
| 在线无电 | `rOnlineWithOutEleCount` | 同上 | RTU 运行指标中的细分状态 |
| 未计算 | `rOnlineNoCalCount` | 同上 | 下游未完成状态计算的数量 |
| 单灯控制器总数 | `AllControlCount` | `/lLamppost/newGetTotalStatus` | `单灯节能管理` → `单灯监控` → `运行状态` |
| 控制器在线/离线 | `OnlineCount` / `OfflineCount` | 同上 | 页面上方控制器状态统计 |
| 灯具总数 | `AlonelampCount` | 同上 | 灯具统计 |
| 开灯/关灯 | `OpenLampCount` / `CloseLampCount` | 同上 | 当前开关状态统计 |
| 告警灯杆 | `alarmLampPostCount` | 同上 | 单灯告警状态统计 |
| 观察时间 | `observedAt` | AgentBridge | 请求完成时的服务器时间，不是设备最后采集时间 |

### 5.4 网页核对步骤

1. 进入 `智能监控管理` → `常用列表`。
2. 抄下页面上方 RTU 总数、在线、离线、电源停电和未启用数量。
3. 进入 `单灯节能管理` → `单灯监控` → `运行状态`。
4. 抄下单灯控制器总数、在线、离线、灯具总数、亮灯、灭灯和告警灯杆数量。
5. 记录核对时刻。若相差 1 至数条，刷新一次 Workspace 或网页后再比，先排除实时变化。

### 5.5 通过标准

- 每个数字与对应页面统计卡一致；
- 回答注明观察时间和上海时区；
- 不把观察时间说成设备采集时间；
- 不使用减法编造下游没有返回的状态数。

## 六、资产列表和详情

### 6.1 发送请求

依次发送：

> 查找照明系统里的 RTU，先列 5 条。

> 查看上面第 1 台 RTU 的详情。

> 查找照明系统里的控制柜，先列 5 条。

> 查看上面第 1 个控制柜的详情。

> 查找照明系统里的灯杆，先列 5 条。

> 查看上面第 1 个灯杆的详情。

### 6.2 预计回答与字段来源

| 资产 | 列表预计字段 | 详情增加的字段 | 照明系统来源 |
| --- | --- | --- | --- |
| RTU | ID、编号、名称、型号、类型、控制柜、分组、工区、状态 | 安装日期、出厂日期、质保、厂家、最后在线、备注、继电器和回路 | `/rRtu/getDataByCondition`；继电器来自 `/rRturelay/getDataByCondition` |
| 控制柜 | ID、编号、名称、道路、路侧、工区、地址、容量、电气类型 | 变压器类型、电表号、组织、经纬度、创建时间、备注 | `/rControlCabinet/getDataByCondition` |
| 灯杆 | ID、编号、名称、道路、路侧、控制柜、工区、灯具数 | 类型、高度、材质、RTU、变压器、地址、经纬度、创建时间、备注 | 列表 `/lLamppost/getDataByConditionForFacilityEx`；详情 `/lLamppost/getLampPostDetail` |

列表中的 `总数` 取分页接口的总记录数；“先列 5 条”只限制展示条数，不改变总数。RTU 详情中的
`继电器总数` 来自继电器接口的总数，`回路数` 是 AgentBridge 对每个继电器下的开关和回路结构计数。

### 6.3 网页核对步骤

1. RTU：`设施资源管理` → `监控设备管理` → `RTU管理`。在 RTU 编号或名称中输入 Workspace
   返回的值，核对名称、型号、类型、控制柜、分组、安装日期和出厂日期。
2. 控制柜：`设施资源管理` → `照明设施管理` → `控制箱管理`。按名称搜索，核对编号、容量、道路、
   路侧、工区和地址。
3. 灯杆：`设施资源管理` → `照明设施管理` → `灯杆管理`。在灯杆编号中搜索，核对灯杆类型、高度、
   灯源数量、道路、路侧和控制柜。
4. 详情核对只点击目标行的查看入口。不要点击编辑、删除、批量设置。
5. RTU 的继电器和回路如果在详情页分标签展示，要逐个展开核对；页面没有数据时回答也应为空。

### 6.4 通过标准

- 三种资产没有混淆；
- 列表的总数、前 5 条稳定编号与网页一致；
- “上面第 1 个”能沿用当前任务上下文，不要求提供内部 `asset_id`；
- 详情来自同一资产，空字段不从相邻设备推断；
- RTU 继电器和回路结构与网页一致。

## 七、RTU 当前运行状态

### 7.1 发送请求

> 列出前 10 台离线 RTU。

> 再看看停电的 RTU。

> 查一台 RTU 的当前状态，带上三相电压和电流。

### 7.2 预计回答

每台 RTU 可能包含：编号、名称、型号、控制柜、工区、分组、道路、状态、最后在线时间、最后巡测
时间、是否告警、是否启用、工作模式、继电器编号，以及三相电压、三相电流、温湿度和漏电电流。

### 7.3 数字和字段来源

| 内容 | 来源与口径 |
| --- | --- |
| 总数 | `/rRtu/getRtusByConditionNew` 对当前状态筛选返回的分页总数 |
| 本次返回 | 当前页实际展示的 RTU 条数，最多为请求中的 10 条 |
| 在线/离线/停电/未启用 | 下游状态筛选和记录中的 `rtuRunningState`，不是 AgentBridge 自行判断网络 |
| 三相数据 | 记录内 `coplogPhase` 的 Ua/Ub/Uc、Ia/Ib/Ic |
| 是否告警 | `isAlarm` 或告警列表是否非空 |
| 最后在线/巡测时间 | `lastOnlineTime`、`coplogTime/lastCoplogTime` |
| 截断 | 需要本地组合筛选且命中数超过单次扫描上限时才为真 |

### 7.4 网页核对步骤

1. 进入 `智能监控管理` → `常用列表`。
2. 点击“离线”状态卡，核对总数和前 10 台的编号、名称。
3. 再点击“电源停电”状态卡，核对第二条回答。
4. 清除状态筛选，按第三条返回的 RTU 编号搜索。
5. 核对状态、巡测时间、三相电压、三相电流、控制柜、分组和告警标记。

### 7.5 通过标准

- 离线和停电是两个下游状态，不互相替代；
- 总数与页面筛选总数一致，展示条数不超过 10；
- 页面为 `--` 的电气数据没有被编造；
- 无结果时明确说未命中，不切换到静态资产列表凑数。

## 八、单灯当前运行状态

### 8.1 发送请求

> 列出前 10 个离线的单灯控制器。

> 看看当前开灯的单灯，先列 10 条。

> 看看当前有告警的单灯。

### 8.2 预计回答与字段来源

外层每条记录是一根灯杆，可能包含灯杆编号、道路、路侧、工区、控制柜、RTU、控制器状态、最后
活动时间、灯具数量和是否告警。灯杆内每盏灯可能包含灯号、用途、开关状态、电压、电流、功率因数、
有功功率、调光值、能耗和漏电电流。

所有记录来自 `/lLamppost/getLampDetialList`：

- `总数` 是当前筛选条件下的分页总数；
- `控制器在线` 是灯杆下真实灯具控制器状态的归纳；
- 任一灯具存在告警时，灯杆记为有告警；
- 任一灯具开灯时灯杆状态为开灯；全部可识别灯具关灯时为关灯；都没有状态时为未知；
- 组合筛选需要有界读取后本地过滤，回答会显示 `downstreamTotal` 和是否截断。

### 8.3 网页核对步骤

1. 进入 `单灯节能管理` → `单灯监控` → `运行状态`。
2. 先选择控制器“离线”，核对总数和前 10 根灯杆。
3. 再选择“亮灯”，核对第二条结果。
4. 选择告警或异常条件，核对第三条结果。
5. 展开一根灯杆，核对每盏灯的开关、电压、电流、功率因数、有功功率和调光值。

### 8.4 通过标准

- 灯杆与灯具的层次清楚，不把 10 根灯杆说成 10 盏灯；
- 离线、开灯和告警筛选与网页一致；
- 电气值只在下游真实返回时展示；
- 组合筛选若截断，回答明确说明，不能声称全量。

## 九、RTU 告警列表和当前备注

### 9.1 发送请求

> 列出最近 5 条 RTU 告警，按发生时间排。

> 告诉我上面第 1 条告警的当前备注。

> 再列最近活动的 5 条 RTU 告警。

### 9.2 预计回答

告警列表应包含告警 ID、首次发生时间、最近活动时间、设备、设备编号、告警类型、级别、状态、内容、
工区、工区提交状态和分组。第一条和第三条可能不同：

- 普通“最近告警”按首次发生时间 `occurredAt` 全局倒序；
- 明确说“最近活动”才按 `lastActivityAt` 全局倒序；
- 最新时间存在多条并列告警时，应说明并列组，不静默选择一个作为写操作目标。

### 9.3 数字和字段来源

| 内容 | 来源与口径 |
| --- | --- |
| 告警总数和列表 | `/rHisHitchAlarm/getDataByRtuAlarm` 的 `RtuHisHitchAlarm` 分页结果 |
| 今日告警、未处理、昨日告警 | 同一接口顶层的 `todayAlarm/untreated/yesterdayAlarm` |
| 上述三个汇总 | 当前系统快照，不受当前页、关键词或日期筛选约束，不能与列表总数直接相减 |
| 首次发生时间 | `occurDate` 等下游首次时间字段 |
| 最近活动时间 | `lastDate/lastTime`；没有时才回退到首次时间 |
| 当前备注 | `/rHisHitchAlarm/getRtuAlarmRemark` 按精确告警 ID 权威读取 |

### 9.4 网页核对步骤

1. 进入 `智能监控管理` → `查询统计` → `RTU报警记录`。
2. 第一条保持默认发生时间排序，核对前 5 条告警 ID、RTU、类型和首次发生时间。
3. 查看页面是否存在相同首次时间的并列记录，核对 Workspace 没有漏掉并列说明。
4. 在第一条目标记录的“备注”列或只读详情中核对当前备注，不点击保存。
5. 将网页排序口径改为末次发生或最近活动，再核对第三条。

### 9.5 通过标准

- 两种时间语义没有混淆；
- 页面总数、前 5 条标识和时间一致；
- 状态显示业务文字，不只返回数字代码；
- 备注读取不弹字段卡或授权卡，也不修改备注；
- 当前快照汇总没有被解释为当前筛选结果。

## 十、RTU 告警分析

### 10.1 发送请求

> 分析最近 30 天的 RTU 告警。

> 分析最近 7 天当前未解除的 RTU 告警。

### 10.2 预计回答

回答通常包含：日期范围、下游总数、取回条数、实际分析条数、是否截断、状态分布、告警类型排行、
设备排行、每日趋势和最近记录。

### 10.3 每个数字从哪里来

| 数字 | 含义 |
| --- | --- |
| `downstreamTotal` | 照明告警接口在日期和下游状态筛选后的总记录数 |
| `retrievedCount` | AgentBridge 实际从分页接口取回的原始条数，最多 500 |
| `analyzedCount` | 取回后再应用告警类型等本地筛选的条数 |
| `truncated` | `downstreamTotal > retrievedCount`，表示只分析了前 500 条以内的样本 |
| 状态、类型、设备排行 | AgentBridge 对 `analyzedCount` 条记录分组计数 |
| 每日趋势 | 按所选时间字段把分析记录按日期计数 |
| `snapshot` | 接口同时返回的当前系统快照，不是最近 30 天的分组结果 |

### 10.4 网页核对步骤

1. 在 `RTU报警记录` 页面填写相同开始日和结束日。
2. 第二条再选择当前告警或未解除状态。
3. 记录页面总数并导出页面结果，按告警类型、RTU 和日期做简单透视统计。
4. 若 Workspace 显示未截断，排行计数应能与全量导出核对；若显示截断，只核对已分析样本的前几条
   和范围说明，不能要求排行等于全量。

### 10.5 通过标准

- 日期范围和状态筛选正确；
- 三个条数和截断关系解释清楚；
- 趋势、类型和设备排行能从分析样本复核；
- 不把分析结果说成照明网页原生统计卡。

## 十一、单灯告警列表和分析

### 11.1 发送请求

> 列出最近 7 天的单灯告警，先看 10 条。

> 分析最近 30 天的单灯告警。

> 异常亮灯有几条？

### 11.2 预计回答与数字来源

单灯告警来自 `/lHisHitchAlarm/getDataByCondition`，字段包含告警 ID、首次发生时间、最近活动时间、
灯杆、灯具用途、道路、路侧、控制柜、工区、告警类型、状态和漏电读数。

列表和分析会先有界读取最多 500 条，再按告警类型、道路、工区或控制柜筛选：

| 数字 | 含义 |
| --- | --- |
| 下游总数 | 相同日期和告警状态下照明接口返回的总数 |
| 取回条数 | 实际取回的原始记录，最多 500 |
| 列表总数或分析条数 | 在取回记录上再应用文字筛选后的命中数 |
| 类型、灯杆、道路、状态排行 | AgentBridge 对命中记录分组计数 |
| 每日趋势 | 按最近活动时间逐日计数 |

### 11.3 网页核对步骤

1. 进入 `单灯节能管理` → `查询统计` → `单灯报警记录`。
2. 设置相同报警日期，核对前 10 条灯杆、道路、灯具用途、告警类型、状态和时间。
3. “异常亮灯有几条”要在告警类型中选择“异常亮灯”后搜索。
4. 分析结果可用页面导出做分组核对；若 Workspace 显示截断，只比较有界样本。

### 11.4 通过标准

- 明确称为单灯告警，不笼统叫漏电；
- 总数、取回数、分析数和截断解释正确；
- “异常亮灯”只在单灯告警页核对；
- 普通单灯告警不会被改写为真实漏电告警。

## 十二、真实漏电语义

### 12.1 发送请求

> 最近 7 天有漏电报警吗？

### 12.2 预计回答

当前正式能力没有把旧的“漏电统计”入口当成真实漏电专表。智能体应采用以下一种合规方式：

1. 在 RTU 告警中按漏电类告警分析最近 7 天；或
2. 要求用户指定一台 RTU，再读取巡测记录中的真实漏电电流；或
3. 明确说明当前没有命中真实漏电记录。

不能使用已弃用的 `smartlight_leakage_summary` 或 `smartlight_leakage_analysis` 把单灯告警冒充漏电。

### 12.3 网页核对步骤

1. 进入 `漏电管理` → `RTU漏电查询` → `RTU支路漏电报警记录`，设置最近 7 天。
2. 同时可在 `智能监控管理` → `查询统计` → `RTU报警记录` 中筛选漏电类告警交叉核对。
3. 如果回答要求指定 RTU，则到 `RTU巡测记录` 查看该设备的漏电电流列。

### 12.4 通过标准

- 回答明确数据来源；
- 没有把异常亮灯、控制器离线等单灯告警称为漏电；
- 两个真实漏电入口均为空时返回空结果，不扩大时间范围凑数。

## 十三、RTU 巡测记录

### 13.1 发送请求

先从第七章选一台名称明确的 RTU，再依次发送：

> 查看这台 RTU 最近 24 小时的巡测记录。

> 只看其中的异常记录。

> 查看这台 RTU 最近 10 天的巡测记录。

### 13.2 预计回答

- RTU 名称命中一台时返回记录；命中多台时先返回候选，不混合查询。
- 默认查询最近 24 小时。
- 每条记录可能包含接收时间、RTU 自身时间、三相电压、三相电流、电流比、功率因数、温湿度、
  继电器电流、回路电流、漏电电流、开关继电器、状态和告警内容。
- 最近 10 天超过单次 7 天上限，应返回范围错误并要求缩短，不执行无界扫描。

### 13.3 数字和字段来源

| 内容 | 来源与口径 |
| --- | --- |
| RTU 候选 | `/rRtu/getRtusByConditionNew` 按名称或编号搜索 |
| 巡测总数和记录 | `/rHisCoplogPhase/getDataByCondition` |
| 总数 | 当前 RTU、时间范围和异常筛选下的分页总数 |
| 接收时间 | `addDateTime/copDate`，是平台收到记录的时间 |
| RTU 时间 | `rtuDateTime/rtuTime`，是设备自身时间 |
| 三相电压、电流 | Ua/Ub/Uc 和 Ia/Ib/Ic 原始字段 |
| 漏电电流 | `LeakCurrents/relayLeakCurrents`，没有返回时保持为空 |
| 异常状态 | 下游 `isSucceeded/state`，不由 AgentBridge 用阈值重算 |

### 13.4 网页核对步骤

1. 进入 `智能监控管理` → `查询统计` → `RTU巡测记录`。
2. 输入 Workspace 锁定的 RTU 编号或名称。
3. 设置相同开始和结束时间；第二条再勾选“仅显示异常”。
4. 对照总数、巡测时间、RTU 时间、Ua/Ub/Uc、IA/IB/IC、状态、告警内容、温度和湿度。
5. 用“显示列”打开漏电、回路或功率因数列。页面没有有效值时 Workspace 也应为空。
6. 第三条不用在网页执行 10 天扫描；AgentBridge 拒绝超过 7 天是预期保护。

### 13.5 通过标准

- 只查询指定 RTU；
- 24 小时和异常筛选正确；
- 平台接收时间与 RTU 自身时间没有混为一个字段；
- 10 天请求被明确拒绝；
- 巡测记录没有被称为巡检任务。

## 十四、巡检任务列表

### 14.1 发送请求

> 看看照明系统最近的巡检任务。

> 只看执行中的巡检任务。

### 14.2 预计回答与字段来源

列表来自 `/inspectionTask/getDataByCondition`，应展示任务 ID、任务名、计划名、状态、巡检人员或组、
开始时间、结束时间、下游进度、昨日进度、已确认设备数、灯杆数、RTU 数、周期和批次。

| 数字 | 正确解释 |
| --- | --- |
| `total` | 当前任务名、计划名和状态筛选下的下游总数 |
| `count` | 当前页实际返回条数 |
| `progress` | 下游直接给出的任务进度，原样展示 |
| `confirmedDeviceCount` | 下游给出的已确认设备数 |
| `lampPostCount`、`rtuCount` | 两种设备的独立计数 |

### 14.3 网页核对步骤

1. 进入 `巡检管理` → `数据统计` → `巡检任务统计`。

4. 对照页面原样显示的整体进度、设备数、巡检组和人员，不自行换算。

### 14.4 通过标准

- 待执行和执行中状态解释正确；
- 任务列表和 RTU 巡测没有混淆；
- 下游进度原样展示，没有用设备数量重新计算；
- 巡检组没有被冒充为单个负责人。

## 十七、连续追问、刷新和历史消息恢复

### 17.1 发送请求

在同一个 Workspace 任务中发送：

> 把刚才离线 RTU 里的第 1 台再查详细一点。

刷新 Workspace 页面后发送：

> 继续分析刚才的单灯告警，重点看最常见的类型。

> 加载更早消息

这里最后一项是页面按钮，不是发给智能体的请求。

### 17.2 预计表现

- 第一条沿用前面离线 RTU 列表中的同一设备；
- 刷新后仍能看到用户输入、智能体回复、任务卡和文件卡；
- 第二条沿用前面单灯告警的时间范围和数据来源；
- 较早的纯文字用户输入与图片输入都能恢复；
- 历史很多时，页面顶部出现“加载更早消息”，点击后滚动位置基本不跳动。

### 17.3 数据来源说明

Workspace 页面同时使用两类历史：

1. OpenClaw 最近聊天记录，用于快速显示最近会话；
2. AgentBridge 持久时间线，用于恢复跨端文本、图片、任务状态和文件卡。

持久时间线是长期恢复的权威来源。任务状态事件很多时，不能挤掉聊天文本；本端纯文本和带图片消息
都必须恢复，而不是只恢复带图片消息。

### 17.4 通过标准

- 连续追问没有换设备或时间范围；
- 页面刷新后历史完整；
- 顶部用户输入不再无故消失；
- 不要求用户提供 `task_id`、`interaction_id` 或工具名；
- 已完成任务不长期停留在进行中或等待用户。

## 十九、整体通过条件

同时满足以下条件才算整体通过：

1. 所有正式读取能力都返回真实结果、正确空结果或明确的范围限制；
2. 静态资产、实时状态、RTU 告警、单灯告警、漏电、RTU 巡测和巡检任务口径没有混淆；
3. 页面数字能按本方案追溯到具体入口和字段，AgentBridge 汇总也明确说明样本范围；
4. 全程没有触发照明系统写操作；
5. 没有跨用户或跨系统数据；
6. 没有重复消息、重复卡片、长期运行任务或静默失败；
7. Workspace 刷新后文字、图片、任务卡和文件卡仍可恢复，较早消息可以继续加载。
