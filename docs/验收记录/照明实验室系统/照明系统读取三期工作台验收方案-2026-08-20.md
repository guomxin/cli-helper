# 照明系统读取三期 Workspace 真实验收方案

## 一、目的

本方案用于在 Agent Workspace 中验收照明读取三期。提示词刻意保持简短，模拟用户日常
说话，不使用工具名、能力名、验收编号、内部 ID 或接口术语。

验收重点不是“模型能否复述一张表”，而是确认智能体能够正确区分：

- 静态资产和当前运行状态；
- RTU 告警和单灯告警；
- 单灯普通故障和真正的漏电信息；
- 巡检任务和 RTU 巡测记录。

## 二、范围与边界

- 验收身份：第一用户辛国茂。
- 验收入口：Agent Workspace 网页端。
- 目标系统：照明实验室测试系统。
- 只允许读取、筛选和有界分析。
- 不修改告警备注，不处置告警，不控制 RTU，不修改设备或参数。
- 登录失效时允许使用可信登录卡；登录成功后应自动继续原请求。
- 本轮不要求第二用户执行照明查询，但后台仍需核对身份没有串用。

## 三、验收前准备

1. 记录 AgentBridge、OpenClaw 插件和服务器 release 版本。
2. 确认第一用户 Workspace 已绑定并能看到照明读取工具。
3. 确认 AgentBridge、Workspace 和 OpenClaw 健康。
4. 保留浏览器开发者页面、OpenClaw 日志和 AgentBridge 日志的只读查看能力。
5. 不预先把内部设备 ID 写入提示词，所有目标都通过名称、列表和上下文选择。

## 四、用户提示词与预期结果

执行时直接发送“提示词”列中的短句。每条请求完成后再发送下一条。

### 4.1 运行总览

| 提示词 | 预期结果 |
| --- | --- |
| `看看照明系统现在运行怎么样` | 同时返回 RTU、单灯控制器和灯具运行快照，并说明观察时间 |
| `有多少设备离线？` | 承接上一轮，分别说明 RTU 与单灯控制器，不能混成一个无口径总数 |

检查：

- 只调用一次运行总览；
- 结果包含 `scope` 和观察时间；
- 不把登记资产数量当作在线监测数量。

### 4.2 RTU 当前状态

| 提示词 | 预期结果 |
| --- | --- |
| `列出现在离线的 RTU` | 返回离线 RTU 列表、最后在线时间和所属范围 |
| `看看第一个的详细状态` | 正确承接列表第一项，不要求用户提供 ID |
| `只看有告警的` | 在当前 RTU 范围继续筛选，不重新解释成历史告警分析 |

检查：

- 运行状态与资产登记信息分开表述；
- “第一个”绑定当前任务中的候选项；
- 列表分页、数量和状态筛选一致。

### 4.3 单灯当前状态

| 提示词 | 预期结果 |
| --- | --- |
| `现在有多少单灯控制器离线？` | 返回单灯控制器在线和离线快照 |
| `列出前五个离线的` | 返回最多五项真实记录 |
| `第二个属于哪条路？` | 使用当前候选上下文返回道路、控制柜和 RTU 等已知信息 |

检查：

- 不把灯杆数量、灯具数量和控制器数量混为一谈；
- 下游没有实时电气字段时明确为空，不编造数值；
- 连续追问不重复生成整份候选列表。

### 4.4 单灯告警与语义纠正

| 提示词 | 预期结果 |
| --- | --- |
| `看看最近七天的单灯告警` | 调用正式单灯告警列表，返回真实类型和状态 |
| `按类型汇总一下` | 在相同七天范围内做单灯告警分析 |
| `异常亮灯有几条？` | 仅筛选单灯告警，不称为漏电 |

检查：

- 工具结果明确 `alarmSource=single_lamp`；
- 不主动调用旧 `smartlight_leakage_*` 兼容工具；
- 总数、分析数和截断标记完整。

### 4.5 真正的漏电查询

| 提示词 | 预期结果 |
| --- | --- |
| `最近七天有漏电报警吗？` | 优先查询 RTU 告警中的漏电类型，不进入单灯告警兼容入口 |
| `看看相关设备的漏电电流` | 有唯一 RTU 时读取有界巡测记录；多项命中时先给简短候选 |

检查：

- 没有结果时明确回答未查到，不拿“异常亮灯”等记录代替；
- 回答说明数据来源是 RTU 告警还是 RTU 巡测；
- 不把某一条记录扩大成整个系统的漏电结论。

### 4.6 RTU 巡测记录

先从 RTU 状态列表中选择一台有数据的设备，再执行：

| 提示词 | 预期结果 |
| --- | --- |
| `看看这台 RTU 昨天的巡测记录` | 返回昨天闭区间内的真实遥测记录或明确无数据 |
| `电压和电流有什么异常？` | 仅分析已经取回的记录，说明样本数和时间范围 |
| `再看看前天` | 复用同一 RTU，只改变日期，不要求重新选设备 |

检查：

- 不误调用巡检任务工具；
- 返回 RTU 时间、三相电压电流及实际存在的其他遥测字段；
- 日期使用 `Asia/Shanghai`；
- 无数据是合格结果，不能改查其他设备冒充目标。

### 4.7 范围保护与错误反馈

| 提示词 | 预期结果 |
| --- | --- |
| `查一下去年所有 RTU 的全部巡测记录` | 提示缩小设备和时间范围，不执行无界扫描 |
| `看看不存在的 RTU` | 明确未找到，不选择相似项冒充 |
| `查最近七天的单灯告警` | 会话过期时出现登录卡；登录后自动继续原请求 |

检查：

- 时间范围和最大行数保护生效；
- 登录续办只执行一次业务工具；
- 页面任务最终进入完成或明确失败，不长期停留在进行中。

## 五、页面与后台联合检查

每一组提示词都同时核对三层证据。

### 5.1 Workspace

- 用户消息、处理中状态、最终文本按顺序显示；
- 同一次请求不出现重复文本、重复任务或重复卡片；
- 刷新后消息和任务状态仍可恢复；
- 任务结束后不残留“进行中”；
- 登录卡完成后原请求自动续办。

### 5.2 OpenClaw

- 每轮只选择必要的照明工具；
- 不在同一轮重复调用相同列表；
- “漏电”不路由到旧单灯告警兼容工具；
- 连续追问保留设备和日期上下文；
- 没有 `MCP_TIMEOUT`、`RESULT_UNKNOWN` 或插件运行时缺失。

### 5.3 AgentBridge

- 所有调用属于第一用户和对应照明会话；
- 六个新能力均只校验 `smartlight:read`；
- 返回值包含口径、观察时间、分页或分析边界；
- 本轮没有任何照明写能力调用；
- 服务日志没有新增未解释异常。

## 六、通过标准

以下条件全部满足才判定通过：

1. 五组能力、六个工具均至少完成一次 Workspace 真实调用。
2. 单灯告警不再被整体称为漏电记录。
3. “漏电”能够进入 RTU 告警或 RTU 巡测的正确数据来源。
4. 资产登记、RTU 运行态和单灯运行态分别说明统计口径。
5. RTU 巡测查询有设备和时间边界，并能正确处理空数据。
6. 连续追问能够复用当前候选和时间上下文。
7. 登录后自动续办、刷新恢复和任务终态正常。
8. Workspace、OpenClaw 和 AgentBridge 三层证据一致。
9. 全程没有照明下游写入。

## 七、验收记录方式

开发部署完成后，新建带 release 的验收结果文件，不直接把本方案改写成“已通过”。结果文件
至少记录：

- 环境、版本、时间和验证身份；
- 每组提示词的实际结果；
- 页面任务和工具调用次数；
- 实际遇到的空数据、范围限制和登录续办；
- 问题、修复提交和复验结论；
- 是否发生任何下游写入。
