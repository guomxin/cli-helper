## 4. 数据口径核对

### 4.1 系统概览

- `cabinetTotal=36`
- `lampPostCounts.searchable=131`
- `lampPostCounts.mapDetail=116`
- Workspace 最终回答正确区分了可检索灯杆和地图明细，没有继续沿用旧的单一 `lampPostTotal=116` 口径。

### 4.2 RTU 告警

适配器声明按 `lastTime` 在返回页内倒序，但最终回答只显示了 `time`，即告警发生时间。两条记录的 `lastTime` 可以相同，而 `time` 不同，因此按 `lastTime` 排序后展示 `time` 会让用户看到非倒序结果。

综合查询中返回的两条记录展示为：

1. `2026-08-10 10:05:38`
2. `2026-08-11 14:15:01`

后台原始结果中二者的 `lastTime` 均为 `2026-08-12 16:30:01`。这不是简单排序代码未执行，而是**排序口径和展示口径不一致**。

### 4.3 巡检任务

原始结构返回：

- `confirmedDeviceCount`
- `lampPostCount`
- `rtuCount`
- `progress`
- `inspectionGroup`
- `state`
- `startTime` / `endTime`

模型将 `confirmedDeviceCount / (lampPostCount + rtuCount)` 自行表述为“完成数/总数”，但系统还单独返回 `progress`，二者显然不是同一统计口径。例如：

- 已确认设备 8，灯杆 16，RTU 1360，系统进度 87.50%
- 已确认设备 5352，灯杆 5352，RTU 0，系统进度 0.28%

后续应直接展示“已确认设备数、灯杆数、RTU 数、系统进度”，不要生成未经系统定义的“完成数/总数”。

### 4.4 漏电记录

- `last_days=30` 由服务端按 `Asia/Shanghai` 计算为闭区间 `2026-07-14` 至 `2026-08-12`。
- `rangeSummary.recordTotal=11` 表示范围内记录数。
- `summary` 为当前系统快照，今日 1、昨日 10、未处理 20，不应用日期范围。
- 明确日期、空范围和反向日期均有正确反馈。

## 7. 问题清单

### P1：巡检状态筛选异常且任务不收口

- `state=2` 和 `state="2"` 均稳定复现 `unhashable type: 'list'`。
- OpenClaw 得到的是非结构化工具错误。
- Workspace 最终文字已结束，但 Task Hub 永久显示进行中。

建议：修复 Smartlight 状态筛选响应的归一化，并确保 MCP 工具异常统一转换为结构化失败，同时由 Host Task 在异常路径进入 `failed`。

### P1：RTU 最近告警的排序与展示字段不一致

- 适配器按 `lastTime` 排序。
- 最终回答展示 `time`。
- 用户看到的告警发生时间可能不是倒序。

建议：明确区分“发生时间”和“最近活动时间”。如果用户说“最近告警”，优先按并展示 `lastTime`；如同时需要发生时间，则两者都显示。

### P1：巡检回答生成了未经定义的完成率口径

- 模型自行组合“完成数/总数”。
- 系统 `progress` 与该组合不一致。

建议：在 MCP 描述中明确禁止推导完成率，直接展示系统原始进度及三类设备计数。

### P2：综合任务的卡片标题和部分失败表达不足

- 四工具综合查询只显示首个工具“照明系统概览”。
- 一项失败时，任务卡仍显示整体已完成。

建议：多工具请求由 Host Task 使用用户任务标题，并支持 `partial_success` 或在摘要中显示失败子步骤。

### P2：模型对巡检失败进行了多次无效重试

- 相同状态筛选重复两次，又请求 100 条全量数据一次。

建议：同一轮相同工具错误只允许一次受控恢复；确定性类型错误应直接终止，不做参数不变的重试。

### P2：端到端耗时主要在工具外部

- 单工具通常 1.4 至 4.2 秒。
- Workspace 单项请求通常 18 至 27 秒，RTU 为 37.4 秒。
- 综合查询为 51.9 秒。

建议：后续分别记录模型首响应、工具开始、工具结束和最终回答四个时间点，优先减少模型二次整理与失败重试。
