## 一、结论与适用边界

当前应优先完善发布产物正确性、完整恢复能力和跨组件任务生命周期一致性，再继续扩展业务能力。建议保留中央治理内核，采用模块化单体逐步收敛职责；不建议在本轮同时推倒重写、拆分微服务或为扩充数量而增加系统。

本次审查覆盖中央任务与登录恢复、OpenClaw 代理和协调器、独立数据库权限与导出、备份发布脚本，以及项目状态、文档导航、运维和验收记录。这是对关键路径的代码与文档交叉检查，不是逐行覆盖全部仓库；未重新执行全量测试、构建或解包线上安装包、登录 OA 或开展压力测试。引用既有验收结果时，均指对应记录中的历史证据，不代表本轮重新执行。

### 1.1 证据与优先级口径

| 口径 | 含义 | 后续处理 |
| --- | --- | --- |
| 已确认事实 | 可由基线代码、配置或文档直接确认 | 可以据此提出改进，但不把潜在影响写成已发生事故 |
| 待验证风险 | 从已确认事实推导出的风险，缺少运行复现或完整调用链证据 | 先建立复现、核对实际产物或检查外部保障，再决定修复范围 |
| 架构与治理建议 | 为降低维护成本、扩容风险提出的设计方案 | 按实际需求评审，避免过度建设 |

本文 P1、P2 为改进工作的相对优先级，不等同于运维事件严重程度。P1 表示优先处理；P2 表示随稳定性建设推进。扩大用户范围、接入高敏数据或提高写入风险时，相关安全事项应提前，不应机械等待第三批。

## 三、第一优先级：产物、发布与恢复

### F01：补齐资源打包，并从安装包验证运行入口

**已确认事实。** [页面脚本加载器](../../bscli/adapters/page_scripts.py)会读取 `seeyon_page_scripts/continue_submit.js` 与 `seeyon_page_scripts/launch_save_draft.js`，分别关联 `ContinueSubmit` 与 `SaveDraft`。[构建配置](../../pyproject.toml)的 `package-data` 明确列出 MCP、Admin、Workspace 资源，但未明确声明这两个适配器脚本。

[验证脚本](../../scripts/Invoke-AgentBridgeValidation.ps1)使用可编辑安装；[部署脚本](../../scripts/Deploy-AgentBridge.ps1)实际构建并安装 wheel，且检查运行模块来自安装目录。因此，源码测试与安装产物测试不是同一个证明。

**待验证风险。** 源码目录能加载资源，不能证明干净构建的 wheel 含有资源。本轮未解包线上 wheel，也未从干净安装环境复现，不能据此宣布线上提交或保存草稿已经故障。

**建议实施。** 先检查干净构建产物清单；按检查结果补齐显式资源声明。增加独立安装测试：构建 wheel，安装到空环境，离开源码目录，调用两个脚本加载入口，核对脚本内容与版本。可评估使用包资源接口替代对源码布局的隐含依赖。

**验收标准。** 两个脚本均存在于产物中，两个加载入口均成功；测试不依赖源码目录、不访问 OA、不执行真实写入。缺少任何必需静态资源时构建验收失败。

### F02：构建必须绑定固定提交，不能只检查跟踪文件干净

**已确认事实。** [固定发布入口](../../scripts/Publish-AgentBridge.ps1)和[部署脚本](../../scripts/Deploy-AgentBridge.ps1)使用 `git status --porcelain --untracked-files=no` 判断工作区状态，随后从工作目录构建 wheel。未跟踪文件被排除在上述检查之外。

**待验证风险。** 位于可发现包目录中的未跟踪 Python 文件可能进入产物，而发布仍标注当前提交。此处是构建边界风险，不能写成已经确认某次发布混入了文件。

**建议实施。** 固定脚本内部从指定提交建立隔离检出或导出目录，在该目录构建。保留原工作区未提交内容，不以删除用户文件的方式获得干净状态。生成制品清单，至少包含提交 SHA、Python 和依赖环境信息、资源清单、wheel 哈希及验证结果。

**验收标准。** 在原工作区增加未跟踪模块后，正式构建不得将其混入；正式制品可追溯到固定提交。独立构建首先要求内容清单和依赖约束一致，不在未处理时间戳等元数据前承诺二进制逐字节可复现。

### F03：将共享环境原位覆盖改成可核验的版本切换

**已确认事实。** [部署脚本](../../scripts/Deploy-AgentBridge.ps1)虽然按 Release 保存 wheel，但实际安装到共享 `$root/venv`，执行安装和检查后再重启服务。该脚本显式启动备份服务的位置在新服务启动并就绪之后，不是本次变更前恢复点。

**待验证风险。** 旧进程仍运行时，其磁盘模块或依赖可能已更新；延迟加载、运行时资源读取和失败回退的状态更难判断。未观察到实际混用事故，不应夸大为必然故障。

**建议实施。** 采用独立版本环境或等价不可变制品机制，按以下阶段推进：

```text
固定提交 → 干净构建 → 独立环境安装 → 离线检查
       → 变更前恢复点 → 受控切换 → 就绪与只读核验 → 确认发布
```

先定义数据迁移与程序版本的兼容范围。程序可回退不代表数据库可以随意回退；不可逆迁移必须明确维护窗口和人工恢复条件。中央代码、宿主代码、纯文档变更应分类，避免纯文档默认触发中央重装和重启。

**验收标准。** 新版本离线检查失败不影响现有进程；切换失败可明确恢复程序版本；不能将未知业务结果改成成功或自动重做。发布记录能区分构建、切换、验证、回退以及数据兼容状态。

### F04：备份清单覆盖恢复所需状态，而不仅是一个数据库

**已确认事实。** [备份服务](../../deploy/systemd/agentbridge-backup.service)经 [CLI](../../bscli/cli/main.py)调用[运行备份实现](../../bscli/core/runtime_backup.py)，备份对象是 `home/agentbridge.db`。独立数据库能力另有以下状态：

| 状态 | 所检查的保存位置 | 依据 |
| --- | --- | --- |
| 数据源目录、状态及版本 | `database/catalog.sqlite3` | [数据源实现](../../bscli/database/sources.py) |
| 按源授权与审计 | `database/grants.sqlite3` | [独立数据库实现](../../bscli/database/independent.py) |
| 报表状态 | `database/reports.sqlite3` | [报表实现](../../bscli/database/reports.py) |
| 数据源凭据密文 | `database/credentials/` | [数据源实现](../../bscli/database/sources.py) |
| 短期报表密文 | `database/reports/` | [受保护存储](../../bscli/core/data_source_secrets.py)、[报表实现](../../bscli/database/reports.py) |

**结论边界。** 所检查的自动备份链不能证明这些状态已被覆盖；是否存在仓库外的额外运维备份，本轮未验证。中央账本校验成功，不等于整个平台可恢复。

**建议实施。** 建立恢复资产清单，将状态分为必须恢复、可重建、允许过期丢弃三类，逐项说明丢失影响、恢复方式与密钥依赖。多个 SQLite 库及密文文件之间要有共同的备份代次和一致性方案；不要把活跃库文件简单复制后当成一致恢复点。密钥独立受控保存，不进入代码仓库或公开制品。

短期报表可以不备份，但恢复后必须将不可交付记录明确收敛为过期或不可用；数据源目录、授权和凭据之间不能出现无法解释的错配。

**验收标准。** 在禁止业务写入的隔离环境中完成恢复，核对用户、数据源、授权、任务关系及密文可用性。记录实际恢复点和耗时，不在演练前承诺 RPO、RTO。异常和缺失项必须显式列出。

## 四、任务连续性与业务质量

### F05：建立真实 Node—Python—SQLite 贯通测试

**已确认事实。** 任务规则分布在[代理工具](../../integrations/openclaw-agentbridge/lib/proxy-tools.js)、[协调器](../../integrations/openclaw-agentbridge/lib/coordinator.js)、[中央服务](../../bscli/core/central_service.py)与[任务账本](../../bscli/core/tasks.py)。普通读取需要独立任务，而由读取触发的登录需要关联原任务，两者必须同时成立。

9 月 19 日新增的[插件用例](../../integrations/openclaw-agentbridge/test/plugin.test.js)覆盖旧钩子存在和缺失、原任务关联及一次续办；但其中 MCP 客户端是模拟实现，中央恢复成功由测试返回。这能证明插件侧行为，不能单独证明真实跨语言调用和数据库提交的整体一致性。它不表示其他中央测试或历史验收没有价值。

**建议实施。** 使用真实 Node 代理与协调器、真实 Python MCP 与中央服务、临时 SQLite，以及可控模拟业务适配器，构建可重复的集成环境。禁止接入真实凭据和生产写入口。

| 场景 | 必须验证的约束 |
| --- | --- |
| 同轮连续两个读取 | 后一读取不复用前一终态任务 |
| 两个读取同时遇到未登录 | 归属不混淆；是否共享认证挑战要有显式规则，各原查询按各自状态收敛 |
| 登录过程中取消查询 | 登录完成不重新激活已取消任务 |
| 登录完成前后宿主或中央重启 | 以中央持久事实恢复，不依赖恰好保留的内存绑定 |
| 重复轮询、回调和通知 | 不重复逻辑完成，不重复授权消费和业务提交 |
| 参数相同与不同的多次查询 | 原操作、参数、幂等域区分明确 |
| 两用户、两系统交错调用 | 不串任务、会话、参数或结果 |
| 租约更新、过期与接管 | 旧协调者不能继续使用失效租约执行 |
| 写入结果未知 | 停止自动重放，只允许核对或恢复通知 |

**契约建议。** 明确原任务、原操作、恢复类型和参数来源；保留同用户、同系统、只读限制及稳定幂等键。可以细化恢复元数据，但不新增模型可见的任意续办工具。不要将读取网络调用的严格一次执行与业务写入的至多一次提交混为一谈：崩溃后的读取重查策略须显式定义，用户反馈和逻辑完成仍须去重。

**验收标准。** 关键执行顺序经过真实组件集成验证，并有任务、操作、交互和时间线的自动断言；写入故障注入不得产生真实副作用。新增测试应证明相关缺陷能被检出，而非仅断言模拟响应成功。

### F06：将 OA 组织树失败作为独立稳定性问题跟踪

**已确认事实。** [最新登录续办验收](../验收记录/原生查询登录续办回归修复-2026-09-19.md)记录首次组织树读取返回 `CAPABILITY_EXECUTION_FAILED`，提示页面未暴露部门树，后续读取成功，根因未确定。

**建议实施。** 在不采集凭据和业务正文的前提下记录页面阶段、目标 frame 是否就绪、是否返回登录页、目标对象是否存在及各等待阶段耗时。区分会话失效、页面未就绪、结构变化、权限不可见和解析失败。只有确认属于安全的瞬时只读失败，才允许有界重试；写入路径不能套用该策略。

**验收标准。** 失败可以归入有依据的错误类型；以脱敏页面样本或模拟页面覆盖慢加载、对象缺失和登录回退。后续成功不能抹去首轮失败记录，也不能把重试成功当作根因已解决。

### F07：为数据库内容分析建立固定质量评测

**已确认事实。** [项目状态](../项目当前状态.md)记录过案例汇总状态夸大，以及宽泛问题下相邻 APP 案例进入主表的相关性限制。查询执行成功与模型结论准确是两个独立指标。

**建议实施。** 复用既有查询与证据结构，建立小规模、可复核的固定评测集。覆盖同名事项、无结果、长文本、分页、相邻但不相关案例、仅有进展而无完成证据、跨时间窗口变化等场景。

评测至少分别判断查询范围是否保留、证据是否完整、相关案例是否混入、结论是否可由原文支持。不得从“提到处理”推断“已经解决”，不得将日志条数等同于人日、考勤或绩效。未覆盖全部记录时必须显式说明。

**验收标准。** 每个关键结论可定位证据；没有完成证据的事项不能判定完成；相关性和完整性错误单独统计。不得为通过评测重新开放已取消的历史结果接口、扩大数据库授权或替换用户要求的查询范围。

### F08：补上报表进程中断后的收敛与独立清理

**已确认事实。** [报表导出](../../bscli/database/reports.py)先写入 `running`，再执行查询、生成 CSV、保存密文并更新 `ready`；普通异常会清理并标记失败。该类中未见用于陈旧 `running` 的执行租约或恢复判断，相同请求键遇到非 `ready` 状态会被拒绝。过期清理在所检查的 `export()` 入口触发。

**待验证风险。** 进程强制退出可能留下无执行者的 `running`，或者文件与状态不同步。还需核对仓库其他位置和外部运维是否已有清理或补偿，不能仅凭本类断言全局不存在。

**建议实施。** 明确运行租约、启动恢复与失败状态转移；区分可核验恢复的已落盘文件与必须重新生成的报表。重新生成仍须检查查询和导出权限、数据源版本及原范围。为过期密文增加不依赖用户再次导出的清理触发，处理孤立文件和清理失败。

**验收标准。** 在写入运行记录后、查询中、文件落盘后、状态更新前等位置强制中断，重启后均有确定结果，不永久显示生成中；不越权重建报表。过期内容按已定义保留策略删除。继续通过用户/数据源隔离、授权变更拒绝、并发预算和 CSV 公式防护测试。

## 五、维护成本与工程治理

### F09：渐进拆分核心职责，不拆散安全事务

**已确认事实。** [中央服务](../../bscli/core/central_service.py)直接导入大量业务适配器、字段 Schema、准备和提交函数，并集中维护业务专属写入定义。[协调器](../../integrations/openclaw-agentbridge/lib/coordinator.js)同时包含登录恢复、计划处理、通知和交付逻辑。风险来自职责和状态耦合，不是单纯文件大小。

建议边界如下：

| 模块边界 | 主要职责 |
| --- | --- |
| 能力与适配器注册 | 能力名称、Schema、效果类型及实现绑定 |
| 受控写执行器 | 授权消费、提交边界、结果未知和权威核验 |
| 读取恢复服务 | 原查询关联、恢复策略、参数和幂等 |
| 任务与计划服务 | 状态转换、取消、父子及步骤关系 |
| 时间线与交付服务 | 消息持久化、通知和文件交付去重 |

**实施边界。** 先补特征测试，再逐个边界移动代码；不与新业务、大规模格式化同时进行。模块可以拆开，但取消与授权消费等原有原子性要求必须保持，不能变成多个互不协调的数据库提交。暂不引入额外微服务、消息系统或通用 DAG 引擎。

**验收标准。** 外部工具契约与权限不变，固定回归通过，事务和幂等边界不退化；新增业务不再要求修改多个无关生命周期分支。

### F10：完善候选制品检查，不把已有测试当作缺失

**已确认事实。** [全量验证脚本](../../scripts/Invoke-AgentBridgeValidation.ps1)已有 Python、编译、依赖、Workspace Node 和插件检查。[文档测试](../../tests/test_documentation.py)已有链接、目录、中文命名，以及构造能力注册表和 MCP 后核对正文总数的测试。

审查时主分支根目录未见 `.github` 目录，分支元数据返回未保护且无必需状态检查。这只是当时仓库可见配置，不足以证明不存在外部 CI、组织级规则或人工检查，也不是对将来状态的断言。

**建议实施。** 优先补安装包测试与跨语言集成测试，生成绑定提交及构建输入的验证清单。`-SkipValidation` 应复核已有结果确实对应同一候选与关键输入，而不是只相信此前对话中“测试已通过”。明确跳过项，避免将跳过计入成功。

当前[发布协议](../部署运维/发布操作手册.md)是部署与验收成功后才推送 `main`。引入分支保护时应同时设计候选分支或不可变制品的验证、部署与晋升顺序；不要只打开保护开关，制造线上已发布但主分支无法更新的新失配。初期可复用已有脚本，不必重建第二套独立发布流程。

**验收标准。** 未验证候选不能冒充已验证版本；验证失败阻断正式晋升；产物、提交和结果可以相互核对；无真实凭据的 CI 仍能完成核心模拟验证。具体平台规则在实施时重新读取，不以本文快照替代。

### F11：让当前事实与历史证据分离，扩展现有文档检查

**已确认事实。** 审查基线的[项目状态](../项目当前状态.md)页首日期为 9 月 16 日，当前插件段落仍写 `0.4.95`，但文档已加入 9 月 19 日修复说明，[对应验收](../验收记录/原生查询登录续办回归修复-2026-09-19.md)为 `0.4.96`。系统表的 `61 + 9 + 4 + 34 = 108` 与正文 `104` 不一致。

这里首先需要核对口径，不能直接把总数改成 108。已迁出、兼容、内部提交和动态数据库能力可能采用不同计数边界。现有文档测试检查正文总体数量，并未因此自动保证各表格分项、当前版本和日期都一致。

**建议实施。** 将当前事实区分为代码已实现、已部署、自动验证通过、真实业务验收通过。版本和能力分项尽量从发布清单及注册表生成，人工只维护范围、风险、阻塞和证据解释；表格和正文采用同一口径。历史验收保持带日期快照，不把多个历史版本堆入当前结论。

本文件是待实施计划，不应成为第二份实时版本总表。[文档导航](../文档导航.md)和当前状态仍承担原有入口职责。

**验收标准。** 在现有测试上增加分项合计、版本来源和状态字段检查；历史数字不误当成当前数字；“代码通过”不自动等于“线上通过”。本文记录的旧值保留为基线证据，后续修复用新验收链接说明。

## 六、扩大试点前的安全边界

### F12：明确下游明文传输例外及退出条件

**已确认事实。** [服务单元](../../deploy/systemd/agentbridge.service)对照明下游配置 HTTP 和显式不安全传输许可；[数据源校验](../../bscli/database/sources.py)保留特定旧源关闭 TLS 的例外。前端和 MCP 使用 HTTPS，不等于所有下游链路均已加密。

本轮未核验是否有额外 VPN、专线或其他补偿控制，也未进行网络抓包，不能据此断言已经发生流量泄露。

**建议实施。** 建立例外清单，记录链路、数据类型、补偿措施、责任角色、复核时间和退出条件；优先迁移为可验证的 TLS。暂不能迁移的下游必须明确可接受范围，不能用“内网”替代风险说明。

**验收标准。** 每条例外都有可核查的保护方案及范围限制；证书错误不能通过静默降级绕过。新环境默认不继承旧例外。

### F13：统一连接、读取和长连接的资源预算

**已确认事实。** [TLS HTTP 服务](../../bscli/core/tls_http.py)基于 `ThreadingHTTPServer`，握手完成后设置 `settimeout(None)`。这本身不能证明已存在可利用的资源耗尽问题；还需核对各请求处理器、网络入口及服务管理器的限制。

**建议实施。** 区分握手、请求头、请求体、普通响应和 SSE 的超时及容量；限制并发线程、每用户连接、请求体大小与待处理队列。长连接应有独立策略，避免修复普通请求超时后破坏正常流式输出。必要时引入受控反向代理或更合适的服务运行层，但先明确最小改动方案。

**验收标准。** 在隔离环境测试慢速连接、断流和并发请求；资源使用有上界，健康检查仍可服务；SSE 正常恢复，认证、Origin 和代理信任边界不被削弱。

### F14：分离通用代码、环境配置与业务验收证据

**已确认事实。** 审查时仓库为公开仓库，部署文件与文档包含实际环境路径、端点和运维布局。本轮未确认发现可复用密码、令牌或私钥，不把配置可见性描述为已发生凭据泄露。

**建议实施。** 公共仓库保留通用模板、参数说明、非秘密验证规则与脱敏证据；真实环境配置进入受控配置管理。补充秘密扫描和人工复核。继续保留不提交业务明细、会话密文和临时卡片 URL 的约定，不以扫描工具通过替代数据审查。

**验收标准。** 示例可用于新环境但不默认指向真实业务目标；发布时显式选择受控配置；敏感内容不进入 Git 历史和公开制品。是否清理既有历史应单独评估，不能未经确认重写仓库历史。

用户级 Worker、企业身份、密钥管理和异机灾备等已在[后续增强事项](./后续增强事项.md)中列明。本文补充具体落点，不把这些既有规划重复宣传为新发现，也不要求本轮一次性全部实现。

### 7.1 每项改进的交付要求

每项工作至少保留：问题编号与基线、代码或文档证据、复现或未复现说明、限定修改范围、自动验证结果、跳过项、是否需要真实业务验收、发布及回退边界。最终状态建议使用“待验证、待实施、实施中、待验收、已完成、暂缓并接受风险”。暂缓必须说明理由和重新评估条件。

### 7.2 实施约束
