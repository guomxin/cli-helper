# 浏览器扩展连接故障处理

## 适用范围

这里指 Codex 当前使用的 Chrome 控制扩展，不是 AgentBridge 已退役的旧浏览器桥。
用于恢复开发与 Workspace 页面验收，不改变业务身份、权限和中央 OA 登录会话。

## 2026年9月8日超长会话诊断

原先“失效标签页重新领取或新开页”的方法只解决了连接恢复，没有解释复发原因。
本轮发现另一条需要优先排查的路径：Codex 浏览器运行时读取超大的当前会话历史，
持续占用 CPU、内存和文件读取资源，使轻量页面调用也可能来不及派发。

| 证据 | 实测情况 |
| --- | --- |
| 运行版本 | Codex 桌面 `26.901.6511.0`，浏览器工具包 `26.901.51231`，扩展 `1.26.901.11451` |
| 当前会话历史文件 | 约 2.11GB，仅检查文件大小，未读取聊天正文 |
| 浏览器 `trusted-worker` | 无操作时约占用一个 CPU 核，工作集约 2GB |
| 重置后复现 | 官方 `js_reset` 退出旧进程后，在同一长会话重新初始化，新进程再次高占用 |
| 文件读取采样 | 新进程在约 5.16 秒内读取 1866.6MB，共 29865 次读取 |
| 最小页面调用 | 仅读取页头也出现内部 3 秒截止，随后报 `Debugger unattached` |
| 退出运行时之后 | 浏览器工具高占用进程消失，Chrome、两个用户登录和 Gateway 均保持不变 |

只读检查当前工具包发现：历史跟踪器从偏移量 0 开始，以 64KiB 分块读至文件末尾，
拼成一个字符串后才解析并推进偏移量；读取或转换异常时不推进偏移量，后续轮询会重读。
这与实测读取压力高度吻合，但尚未捕获具体异常堆栈或逐文件 I/O 跟踪，
不能把每一次断连都归因于这一条路径。文件字节数与 JavaScript 字符串长度并非同一单位，
不能仅凭文件大小断言已捕获字符串超限异常。

### 恢复与验证边界

1. 先区分浏览器工具进程和 OpenClaw Gateway，不能因为看到多个 Node 进程就批量结束。
2. 对持续高占用的浏览器控制会话使用官方 `js_reset`，保留 Chrome 窗口及用户登录。
3. 已确认超长会话反复触发高占用时，不继续在原会话反复初始化工具或新建浏览器标签页。
4. 经用户授权，用不复制旧历史的独立短诊断会话控制同一批页面，比较调用成功率、耗时和空闲资源占用。
5. 独立诊断必须确认实际运行时关联的是新会话；工具名称可见、子助手已创建，不等于浏览器会话已隔离。
6. 短会话恢复是运用侧规避，不等于签名扩展或产品运行时已修复；未通过对照测试不得写成“已根治”。

不编辑签名扩展、缓存工具包或自动生成配置，不关闭历史跟踪、生命周期清理和安全检查，
不裁剪或删除原会话历史，不复制普通与无痕用户的 Cookie。
产品侧应改为有界流式解析、有限的未完整行缓存、安全的偏移量推进和错误退避，
避免每次从头读取全部历史。没有正式升级修复之前，保留诊断结论的适用版本与限制。

本次脱敏现场记录保存在工作区 `output/Chrome扩展超大会话读取诊断-2026-09-08.md`。
官方也列出新建 Codex 聊天以清理聊天关联连接状态的排查方式：
[浏览器扩展故障排查](https://learn.chatgpt.com/docs/chrome-extension)。

### 短诊断助手的对照结果

不复制历史的独立助手成功启动新浏览器运行时。在约 127 秒采样中，单核 CPU 平均约
0.48%，内存约 84MiB，读取增量约 0.458MiB，未复现长会话的资源异常。
但是两个原 Workspace 标签页均被官方接口拒绝领取，原因是仍归原会话所有。
本轮页面领取 0 成功、3 失败，尚未读取身份或完成连续页面测试，不能写成双用户验收通过。

`js_reset` 退出工具进程不等于释放标签页所有权。当前公开接口文档只说明回合结束时
自动清理未标记的用户页面，没有可在本轮调用的独立释放接口。不能改写内部状态强占页面。
下一步由用户在同一项目新建不复制历史的普通 Codex 会话继续对照；保留原 Chrome 与登录，
先重新发现和领取原页，仍遇所有权错误时如实区分，不把它误称为调试器断连。
详细结果见工作区 `output/Chrome短会话对照验收-2026-09-08.md`。

## 2026年9月7日实测结论

| 检查 | 结果 |
| --- | --- |
| 扩展发现 Chrome 和已打开标签页 | 成功 |
| 原 Workspace 标签页读取 | 重复返回 `Debugger unattached` |
| 重置当前 CUA 控制会话 | 未恢复原页 |
| 扩展安装状态 | 已安装、已启用，无禁用原因 |
| Native Messaging 清单与真实用户注册项 | 正确 |
| 原管理控制台页面读取 | 成功 |
| 使用完整标签页身份重新领取原 Workspace | 仍失败 |
| 同一 Chrome 配置新建 Workspace 页 | 成功，复用 `xinguomao` 登录 |
| 新页导航、历史消息和应用卡读取 | 成功；未发起业务请求 |
| 原页单独刷新 | 控制接口仍报错，原页保留 |

结论：已解除页面测试阻塞，但没有修复原标签页的调试器状态，也不能宣称扩展内部缺陷已根治。
证据将问题缩小到原标签页的控制连接，不支持“扩展未安装”“全部站点无法访问”或“OA 登录失效”的判断。
触发该状态的底层原因尚不明确；不据此猜测是网络、HTTP、证书或用户权限问题。

## 固定恢复顺序

1. 获取当前浏览器与标签页清单，区分普通窗口的第一用户和无痕窗口的第二用户。
2. 先直接控制用户已打开的指定 Workspace；一次明确的连接失败后，不反复操作同一失效对象。
3. 先刷新当前浏览器的 `browser.user.openTabs()`，匹配原页的完整 `providerTabId`、标题及 URL，调用 `browser.user.claimTab(tabInfo)` 重新领取原页，再作一次只读状态复测。仅反复按编号 `getTab` 或重置 REPL 不等同于重新领取。9月8日下午此方法恢复了第二用户旧无痕页，未新开页或重新登录。
4. 重新领取仍失败，再尝试在原浏览器、同一身份上下文新开相同 Workspace 地址的标签页，验证身份和导航。
   若包含建页、导航及初始读取的单次调用超时，将三步拆开调用；先保存新页句柄，再导航，再读取状态，避免超时后重复建页。2026年9月8日以此方式恢复第一用户页面，并实际发起只读组合验收。
5. 新页仍失败，或者工具无法在原无痕窗口开页时，立即请用户协助在相应窗口新开页或恢复连接。不要长时间盲目排查，也不要用第一用户普通窗口冒充第二用户。
6. 用户恢复后继续原定验收，核对请求、应用卡、终态和后台证据；不能因一次连接失败而把任务停在不完整状态。
   如果现有浏览器对象的标签页列表仍未出现用户新页，重新获取全局浏览器状态，再按新标签页编号连接；不要据旧列表断定用户没有开页。9月8日中午按此步骤找到新的无痕页并确认 `lishiyu` 身份。
7. 页面初始加载未完成或可访问性树被截断时，不把空列表或缺少尾部消息判定为数据丢失。
8. 保留需要继续验收的恢复页，不擅自关闭原用户页面、清除站点数据、退出登录或复制 Cookie。安装与 Native Messaging 检查仅在明确需要时进行。

恢复后只对无副作用读取作有限复测；点击提交等写动作如果超时，先核对实际结果，禁止因连接恢复而自动重试。

### 9月8日下午原页恢复证据

第二用户旧无痕页先后在直接连接和重置REPL后返回 `Debugger unattached`。使用实时用户标签清单的完整对象重新领取后，第一次轻量读取出现内部3秒截止，随后DOM快照、任务/对话切换、最近回复读取及原编号接口均恢复。看到的是12:17原有回复，不代表本次重新检查业务登录状态。

当前扩展1.26.901.11451的代码存在默认10秒CDP命令超时后主动断开调试器的路径；后续未连接状态直接报上述错误。外层工具超时与该内部截止不同。此代码证据解释了可能持续失联的机制，但没有捕获每次最初断连的完整原因，不能宣称扩展已永久修复。不得热改签名扩展或无限延长全部内部命令。

上述操作只恢复浏览器控制。真正业务验收仍需分别验证请求、卡片、执行结果和跨端同步。
不要将恢复页面成功当作尚未部署功能的验收通过。

## 安装检查的注意事项

### 9月8日普通与无痕窗口补验

- 普通窗口新建 Workspace 页后，可通过扩展的可访问性接口读取身份、输入请求、切换任务和打开应用卡；实际完成只读查询与测试卡失效后的页面核对。
- 第二用户无痕旧页仍报 `Debugger unattached`。用户在原无痕窗口新开标签页后，扩展成功读取 `lishiyu` 身份，发起 OA 会话查询并看到正确答复。
- 本轮工具的新建标签页接口没有指定无痕窗口的参数。不能用普通窗口的新页代替第二用户，也不能转移 Cookie；遇到这种限制，让用户只在原无痕窗口新开页即可，不要求重新登录 OA。
- 普通新页使用扩展内的 Playwright 读取时曾再次出现调试器未连接；后续新页采用 `getAXState`、`setValue`、`click` 完成验收。这里只记录观察到的差异，不认定 Playwright 调用就是缺陷根因。
- 长聊天的可访问性树可能只返回前 500 个子项。读取不到尾部消息不等于页面没有消息，应切换任务详情并结合后台记录核对，不能据此判断同步失败。
- 在连接正常的新页中，扩展自带的 DOM 快照能补足长聊天可访问性树截断的尾部消息；它仍通过 Chrome 扩展操作当前用户页面，不是启动独立 Playwright 浏览器。

以上证明“同窗口新页恢复”对本轮普通和无痕页面均有效，不等于原页连接故障已经根治。

优先使用当前已安装 Codex 浏览器插件自带的只读诊断脚本：

- `check-extension-installed.js --browser chrome --json`
- `check-native-host-manifest.js --browser chrome --json`

脚本路径包含插件版本，须先定位当前路径，不能把本次版本硬编码进长期自动修复程序。
Windows 沙箱里的 HKCU 不一定是交互用户的 HKCU。本次沙箱检查误报注册项不存在，
正式获准的真实用户上下文只读复核显示清单和注册项完全匹配，因此没有修改注册表。

不要直接编辑 Chrome 配置、删除扩展目录、开放调试端口、放宽站点权限、清除 Cookie，
也不要启动另一套 OA 登录把中央保活会话踢下线。
