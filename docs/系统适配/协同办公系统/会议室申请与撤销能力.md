# OA 会议室申请与撤销能力

## 一、业务边界

OA 左侧“会议室”中的“申请会议室”和“新建会议”是两个动作：

- 会议室申请只包含用途、会议室和使用时间，不创建会议、不邀请参会人、不发送会议通知；
- 新建会议包含主题、参会人、正文和发送，同时可以占用会议室；
- 两者共用会议室目录和占用事实，但不能共用冻结计划或授权卡。

因此，用户说“申请/预订会议室”时进入本能力；用户说“创建会议、邀请人员、发送会议通知”时进入
`oa.meeting.create.prepare`。智能体不得因为两者都涉及会议室而自行替换。

中央 MCP 还执行运行时语义保护：首次调用会议创建工具时，宿主必须显式声明用户要求“创建并发送
会议”。只有会议室名称和使用时间、没有创建或发送会议意图时，会议创建工具会拒绝执行并要求改用
会议室申请工具。该保护对 OpenClaw、Workspace 和其他标准 MCP 宿主一致生效，避免同一会话中的
历史工具调用把后续“预订会议室”错误带入完整会议流程。

## 二、公开能力

### 1. 申请会议室

- 准备：`oa.meeting_room.application.prepare`
- 提交：`oa.meeting_room.application.create`
- 模型可见 MCP：`oa_meeting_room_application_prepare`
- 权限：`oa:write:meeting`

填写卡包含：

- 会议室用途，最多 80 个字符；
- 会议室，选项只来自目标时段实时可用的 OA 会议室；
- 开始时间和结束时间。

字段卡会预填用户已经提供的信息。要生成房间选项，首次调用必须有完整时间范围；没有时间时应先向
用户补问，不能先展示未经查询的固定会议室列表。

### 2. 撤销会议室申请

- 准备：`oa.meeting_room.application.cancel.prepare`
- 提交：`oa.meeting_room.application.cancel`
- 模型可见 MCP：`oa_meeting_room_application_cancel_prepare`
- 权限：`oa:write:meeting`

撤销只接收“我的申请”返回的精确 `application_id`，一次只撤销一条。当前一期只支持独立会议室
申请，不替会议模块撤销关联会议。以下情况失败关闭：

- 申请已关联会议 ID 或会议名称；
- OA 状态已经终止；
- 会议室正在使用；
- 使用时间已经结束或提前结束。

撤销原因通过独立字段卡填写，最终仍需授权卡确认。

## 三、申请执行顺序

```text
解析用户时间和房间意图
  -> roomListInfo 查询实时空闲
  -> 展示预填字段卡和真实房间选项
  -> validateRoomApps 执行 OA 原生规则校验
  -> 冻结房间、时间、用途和“我的申请”基线
  -> 展示最终授权卡
  -> 再查 roomListInfo 并再次 validateRoomApps
  -> 消耗一次性授权
  -> applyRoom
  -> getMyApps 回读一个新的精确申请
```

底层写对象严格保持 OA 原生字段：`roomId`、`appBeginDate`、`appEndDate` 和 `description`。
申请能力不伪造会议主题或参会人字段。

查询到空闲只代表当时快照。若其他人在用户授权前抢占会议室，最终提交会在写边界之前停止，不消耗
授权，也不会强行写入。

## 四、撤销执行顺序

```text
getMyApps 精确定位本人 application_id
  -> 校验独立申请和可撤销状态
  -> 填写撤销原因
  -> 冻结申请身份和状态
  -> 展示最终授权卡
  -> 再次读取同一申请并核对未变化，同时记录占用快照
  -> 消耗一次性授权
  -> cancelRoomApp(operation=0)
  -> 单独记录接口应答；即使应答解析或连接异常，也不重发撤销
  -> getMyApps 与 roomListInfo 双源核对申请消失、进入终止态或解除占用
```

自然语言中的日期默认按会议室使用时间理解。例如“撤销下周一订的五号会议室”先使用“使用日期”
和会议室别名查询“我的申请”，取得唯一的精确 `application_id`；只有用户明确说“某天提交的申请”
时才使用申请提交日期。会议室别名只用于查找，冻结计划和撤销接口始终使用 OA 返回的正式会议室 ID
与申请 ID。

`getMyApps` 在撤销后可能短暂保留旧记录，因此回读使用递增等待，并且只有当同一申请在撤销前
确实存在于会议室占用快照、撤销后又从该快照消失时，才允许以“已解除占用”确认成功。两个事实源
都不能确认时才标记为 `RESULT_UNKNOWN`，且不会自动重试撤销。

写后核验把 `getMyApps` 和 `roomListInfo` 作为两个相互独立的证据源。任一读取接口出现瞬时异常时，
不会立即结束整个撤销任务，也不会阻止另一证据源继续核验；系统只按有限次数重试读取。任一证据源
确认申请消失、进入终止态或解除占用，即返回成功。整个过程中 `cancelRoomApp` 始终只调用一次，读取
重试不得重放撤销写入。

成功结果会记录实际回读轮数、恢复过的读取异常数，以及不含响应正文和地址的安全异常类型。若所有有限重试仍不能确认，操作才进入
`RESULT_UNKNOWN`，内部错误会保留最后失败的证据源与异常类型，便于区分“OA 仍显示活动记录”和
“核验接口暂时不可用”。此时仍禁止自动再次撤销，应等待后续权威查询核对实际状态。

撤销应答与业务结果分开处理：`cancelRoomApp` 的 HTTP 200 空正文或 JSON `null` 只表示进入待核验，
不直接代表撤销成功。无法解析应答、连接中断、HTTP 错误或拒绝提示也不能跳过权威回读，因为写入可能
已经生效。只有一次撤销请求，后续最多七轮只读核验；两类诊断分别记录，禁止自动重放写入。

以“申请消失”为依据时，`getMyApps` 必须提供完整且结构有效的列表：总数稳定、条目 ID 无重复，
数量与总数一致且未截断。占用快照必须包含目标会议室及有效占用数组，且基线中曾出现同一申请。
缺字段、分页截断或不完整集合不能被误当成“已撤销”。其他会议室读接口不接受空正文或 `null`。

成功操作的 `acknowledgement` 保存阶段、HTTP 状态、内容类型、正文形态及长度，不保存响应正文或凭据。
`verification` 保存确认来源、实际回读轮数及安全异常类型。结果未知时错误明确标注回读阶段，并保留
应答异常类型，避免把请求应答问题误诊成回读瞬时错误。

## 五、安全约束

- 申请和撤销均采用“字段卡、冻结计划、最终授权、单次提交、权威回读”；
- OpenClaw、Workspace 和其他宿主只看到准备工具，commit 工具保留在中央可信续办链路；
- 完整会议字段卡标题固定为“填写会议创建信息”，独立申请字段卡标题固定为“填写会议室申请”，
  用户可以在最终授权前直接识别业务边界；
- 权限继续复用既有 `oa:write:meeting`，不扩大当前会议权限持有者的业务域；
- 申请基线、授权和回读绑定同一 `userSubject`、OA 会话与实际下游主体；
- 不开放批量申请、批量撤销、提前结束、催办、审核或会议联动撤销；
- 不把会议室申请混入 OA 已发、已办、待办或跟踪事项。

## 六、验收状态与人工测试

自动化测试覆盖字段预填、真实空闲选项、冲突阻断、OA 原生校验、授权边界、新申请回读、关联会议
拒绝、使用中/已结束拒绝、精确撤销回读、单源瞬时失败恢复、双源独立核验、写入不重放、契约漂移
和结果未知诊断语义；另覆盖 JSON `null`、非 JSON 应答、写后连接丢失、HTTP 错误、拒绝应答、
不完整列表、重复条目、分页总数漂移及无效占用快照。

真实写入必须由用户选择一个不会影响业务的未来时段并完成两次可信授权。建议在 Workspace 或聊天端
发送简短提示词：

1. `查明天下午 2 点到 3 点空闲的会议室。`
2. `申请 3 号会议室，明天下午 2 点到 3 点，用途是智能体测试。`
3. 完成字段卡和最终授权，随后发送：`查看我的会议室申请。`
4. 从返回结果选择刚创建的申请，发送：`撤销刚才的会议室申请，原因是测试结束。`
5. 完成撤销字段卡和最终授权，再次发送：`查看我的会议室申请。`

成功标准是申请后出现一个新的精确 `application_id`，撤销后同一申请离开活动集合或进入 OA 终止态。
在未完成真实申请与撤销前，只能声明代码、模拟契约和只读现场探针通过，不能声明真实写闭环已验收。
