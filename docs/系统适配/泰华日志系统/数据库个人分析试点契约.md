> 更新：2026-09-09。

开发基线见[个人只读分析一期详细设计](./数据库个人只读分析一期详细设计.md)，其中完整性证明、空窗口身份、结果访问与取消规则优先于本试点简要契约。

## 1. 已有证据与试点边界

[本人日志对账](../../验收记录/泰华日志系统/数据库本人日志对账-2026-09-09.md)已证明一个已登录用户、一个完整周的 3 条日报，在本人 API、团队 API 仅本人筛选和数据库之间核心字段一致。全局 status、普通用户权限、项目关联与周报工时规则仍未验证。

在没有后端源码的条件下，首个试点采用“原系统本人 API 可见记录集合 + 数据库确定性计算”。原系统仍决定哪些记录可见，数据库执行器只在该集合内读取和计算，不自行复刻未经验证的完整权限算法。

这是有 API 依赖的过渡契约，尚不能替代大范围数据库直读。达到上限时应缩小窗口，不静默切换为更宽的查询。

## 2. 候选能力与输入

拟议能力 `taihua.analytics.personal.summary`，effect 为 read；建议要求 `taihua:analytics:read`，不由既有 taihua:read 自动继承。在本草案形成时尚未注册；实现后的名称与参数以现行说明为准。

模型仅提供：

```json
{
  "start_date": "2026-08-31",
  "end_date_exclusive": "2026-09-07",
  "log_type": "DAILY",
  "group_by": "day"
}
```

首批约束：日期窗口最多 7 天，必须明确日报类型 DAILY，group_by 仅支持 none/day，API 候选上限 500 条，SQL 语句超时 5 秒。不支持模型传入用户名、user_id、部门 ID、SQL 或表字段表达式。

WEEKLY 已确认为周报，但一期个人工时汇总暂不纳入；后续核实口径后单独发布。窗口限制是试点预算，不是数据库容量结论。

## 3. 可信执行步骤

1. 中央服务校验主体、Scope、数据源与当前应用会话，不使用模型传入的身份。
2. 在当前会话调用本人 API 读取日期窗口，不切换为团队全量接口。响应达到上限、形态异常或无法证明可用范围时，返回范围需缩小/结果不完整。
3. 服务端建立有有效期的可见日志 ID 快照，并绑定中央主体、会话身份、日期窗口和请求。ID 集合不由模型填写或修改。
4. 校验快照内记录均映射到可信的应用 user.id；初次建立映射需交叉核验既有身份信息，不凭同名数据库账号建立关系。空结果不通过猜测 user.id 补查数据库。
5. 使用只读事务、参数绑定、user_id、日期、类型以及可见 ID 白名单共同限制 SQL。记录删除、所有者变化或核心字段与 API 样本变化时，返回 SOURCE_CHANGED，停止给出已核实汇总。
6. 用固定算子聚合，对关键字段前后核对；范围或权限发生变化则失效。跨系统不能宣称原子一致快照，结果记录 API 和数据库采集时间。
7. 返回聚合与证据引用，普通模型不接收正文、角色明细、认证列、SQL 或连接凭据。

status 不作为此试点自行推断的可见性条件。权限来源是原系统 API 可见集合，而不是假设 status=true 一定有效。以后转为独立数据库直读时仍需另外核验 status 和权限算法。

## 4. 参数化查询示意

以下参数由已校验的服务端上下文绑定，不能开放为任意 SQL 工具：

```sql
SELECT log_date,
       count(*) AS log_count,
       sum(hours) AS registered_hours,
       count(DISTINCT user_id) AS people,
       count(DISTINCT (user_id, log_date)) AS person_days,
       count(*) FILTER (WHERE project_id IS NULL) AS no_project_count
FROM public.work_log
WHERE user_id = %(verified_user_id)s
  AND id = ANY(%(visible_log_ids)s)
  AND log_date >= %(start_date)s
  AND log_date < %(end_date_exclusive)s
  AND type_code = %(log_type)s
GROUP BY log_date
ORDER BY log_date;
```

执行前后需要比对 ID、日期、类型、工时和项目关联的变化，不能只检查 count 相等。SQL 中的 fixed user/id 条件是普通结构化查询编译器的内部条件，不能被额外 filters 覆盖。

## 5. 输出与异常

输出包含日报日志条数、登记工时（Decimal 字符串）、有日志人数/人日、每日分布、未关联项目条数、日期范围、类型、授权范围摘要、证据引用与完整性状态。工时缺失、非正值等另列数据质量信息，不静默清洗。

created_at、updated_at 保留数据库原始精度；如提供 API 对照说明，显式标注秒精度与空值差异。不得把 created_at 改名为 submitted_at，不生成迟报率或漏填率。

稳定异常至少包括 IDENTITY_UNVERIFIED、DATA_ACCESS_DENIED、RESULT_INCOMPLETE、SOURCE_CHANGED、SOURCE_UNAVAILABLE、BUDGET_EXCEEDED。空结果只表示原系统该窗口没有返回可见日志，不自动解释为未出勤或漏填。

## 6. 原稿发布门槛（历史）

原稿形成时尚未实现本契约，提出以下验证要求：覆盖空窗口、日期边界、API 上限、日志变化、类型混合、身份冲突和取消；普通用户与管理员分别验证个人范围，不能仅用当前 ADMIN 样本替代。

数据库凭据应进入现有受控密钥配置；账号对敏感表和序列/TEMP 的额外权限按元数据盘点结论收敛。最终用户字段和读取请求摘要脱敏需同步处理。上述条件达到后才注册模型可见能力。
