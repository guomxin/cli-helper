## 1. 一期业务字段映射

| 逻辑字段 | 物理字段 | 类型与约束 | 使用规则 |
| --- | --- | --- | --- |
| 日志标识 | `public.work_log.id` | bigint，主键 | 去重、证据和稳定分页 |
| 日志日期 | `work_log.log_date` | date，非空 | 默认业务统计日期 |
| 登记工时 | `work_log.hours` | numeric(4,1)，非空 | 用 Decimal 保留精度；实际合法范围待核实 |
| 人员标识 | `work_log.user_id` | bigint，非空外键 | 关联人员、落实读取范围 |
| 项目标识 | `work_log.project_id` | bigint，可空外键 | LEFT JOIN 项目，保留未关联项 |
| 正文 | `work_log.content` | varchar(4000)，非空 | 正文权限通过后才读取 |
| 日志状态 | `work_log.status` | boolean，非空 | 尚未确认 true/false 含义，暂不预设有效记录条件 |
| 工作类型 | `work_log.type_code` | varchar(64)，非空 | 已确认 WORK_LOG_TYPE：DAILY 日报、WEEKLY 周报；不直接混合汇总工时 |
| 创建/修改时间 | `work_log.created_at/updated_at` | 无时区 timestamp，可空 | 保留时间语义；不直接命名为提交时间 |
| 迁移来源 | `work_log.legacy_source/legacy_id` | 可空；组合条件唯一索引 | 用于内部迁移对账，不作为全历史覆盖证明 |
| 人员信息 | `public."user".id/username/fullname/dept_id/status` | dept_id 可空外键 | 仅批准列；status 含义待确认 |
| 部门信息 | `dept.id/name/parent_id/status` | 层级外键 | 暂按当前组织树候选，不推断历史有效期 |
| 项目信息 | `project.id/code/name/status` | 名称、编码分别唯一；编码可空 | boolean status 与项目阶段不得混同 |
| 项目来源状态 | `project.oa_source_type/oa_status_value/oa_hidden_reason` | 文本，可空 | 需明确项目选择可见性与历史分析纳入规则 |

`work_log` 无直接部门 ID 或部门历史字段，常规组织关联候选为 `work_log.user_id → user.id → user.dept_id → dept.id`。存在另一条 `dept_users` 关系，确认前不能把两条路径任意合并，以免重复归属或越权。

日志来源还含 `source_channel`、`source_credential_id`、`source_request_id` 等内部追踪字段；业务分析默认不投影 credential/request 标识。人员表中的 password、phone、email、微信及 OA 外部身份等字段不进入默认业务目录。

## 2. 权限与关注组结构

| 物理对象 | 已确认结构 | 必须确认的业务规则 |
| --- | --- | --- |
| `team_log_visibility_rule` | viewer_dept_id、target_dept_id 复合主键，双方关联 dept，有 status | 本部门是否默认可读？是否包含子部门？是否有规则传递？停用语义？ |
| `user_review_depts` | users_id、review_depts_id 复合主键 | 可审阅是否等于可读？是否覆盖下级部门和停用人员？ |
| `project_visible_depts` | project_id、visible_depts_id 复合主键 | 控制项目选项还是日志可见性？无配置代表公开还是不可见？ |
| `role`、`user_roles` | 角色及人员角色关系 | 哪些角色例外？如何与部门规则组合？ |
| `watch_group` | owner_user_id、name、status | 是否仅所有者可用？能否共享？ |
| `watch_group_member` | watch_group_id、user_id 复合主键 | 筛选必须与已授权人员范围取交集 |
| `dept_users` | dept_id、users_id；users_id 唯一 | 与 user.dept_id 的业务优先级和更新一致性 |

这些表均未启用 RLS。结构只能证明规则有存储位置，不能证明完整算法。正式服务需要核对日志系统权限实现或取得所有者确认，并用不同范围用户的 API 结果核验；规则不明时不开放团队全量查询。

关注组关系已找到，可纳入一期候选。实现时按授权成员集合过滤日志，避免一个成员属于多个集合导致重复汇总；关注组的存在不授予额外读权限。

## 3. 业务字典与时间口径

已发现 `dict_type(type_code,type_name,description)`、`dict_item(type_code,item_code,item_name,description,status)`。后续有限字典读取已确认 WORK_LOG_TYPE 下 DAILY 为日报、WEEKLY 为周报，两项 status=true；日报和周报工时关系仍未验证，不能仅按同名列关联或混合求和。

状态字段无数据库注释，不能据布尔类型发布 `status=true` 为有效日志的最终规则。用户确认无法取得后端源码；已对照的三条本人样本均为 true，没有 false 样本，不能据此推导全局状态语义。先按[个人分析试点契约](./数据库个人分析试点契约.md)复用本人 API 的可见集合，其他状态和角色边界通过合法会话与真实只读样本逐步验证。

服务端时区为 Asia/Shanghai，但无时区 timestamp 的业务解释仍需确认。log_date 用日期窗口，created_at/updated_at 按确认后的时区解释；迁移记录的创建时间可能是导入时间，待数据证实。本人样本中 API 创建时间到秒、数据库有小数秒；API 修改时间为空而数据库有值。保留这种差异，不把 API 空值解释为数据库没有时间。

当前结构未证实存在正式提交时间、应填日历、请假豁免或人员部门有效期。漏填率、迟报率、历史组织还原继续列为条件项，不因拿到数据库就直接发布。

## 5. 上线前权限收敛

当前账号可读整个 public，包括认证和令牌相关对象；AgentBridge 必须按表列白名单提供业务数据，不能提供任意 SQL 或全库目录。建议由数据库所有者提供专用受限视图或列权限，给后续生产分析账号进一步缩小范围。

本轮在 55 个表上未发现表级 INSERT/UPDATE/DELETE/TRUNCATE 或列级 INSERT/UPDATE 授权，但账号拥有 TEMP 与 33 个序列的 USAGE，并存在对应的未来序列默认授权。建议所有者核实是否需要保留；默认只读设置不能替代对象权限收敛。盘点没有尝试更改只读设置、调用序列或建表；用户此前反馈完成的写入拦截验证属于用户提供的信息，不属于本轮测试证据。

未来由 postgres 创建的表会被数据库自动授予 SELECT，但不能自动进入能力目录。上线仍以审核后的数据集和固定策略版本为准。
